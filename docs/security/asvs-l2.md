# ASVS verification matrix

Espalier verifies against OWASP ASVS 5.0.0 at tag `v5.0.0_release` of the
[OWASP ASVS repository](https://github.com/OWASP/ASVS/tree/v5.0.0_release/5.0/en).
The target is Level 2, with the selected Level 3 items of README section 6.1:
6.3.5 and 6.3.7 (notifications), 6.3.8 (no enumeration), 6.5.6 (every factor
revocable), 3.4.8 (COOP) and 3.5.8 (Fetch Metadata).

Each row names the tasks that implement the requirement, the owner first and
the extending tasks after it, as the ownership table of task 0004 (step 42)
assigns them. `Code` names the module or document, and `Test` names the test
file that proves it. A requirement the platform deviates from has an entry in
the section "Deviations", and its row takes the status `deviation` once every
task it names has added its code and test.

Status values:

| Status | Meaning |
|---|---|
| `open` | At least one named task has not yet added its code and test. `Notes` states what each task delivers and what remains. |
| `implemented` | Code exists, and the test that proves it is missing. |
| `verified` | Every named task has added its code and its test. |
| `deviation` | The platform deviates on purpose; the section "Deviations" gives the rule and the reason. |
| `not applicable` | The requirement does not apply; `Notes` gives the reason. |

Test files named without a directory lie in `test/espalier/crypto/`; other test files are named with their path.

## Ownership

The ownership table of task 0004 (step 42) names every row of the chapter tables. Each entry assigns its rows to one owning task, named first; the tasks after `extended by` add their code and test to the same rows, and the `Task` column of each row lists the same tasks in the same order. An entry marked `deviation` names its decision of README section 15, and the section "Deviations" gives its rule and reason. The rows after `not applicable` have no task, and the chapter tables give the reason for each. The section "Security requirements" of every task spec lists exactly the rows that this table names for its task, as owner or as extending task (README section 15, decision D16). `test/docs/asvs_matrix_test.exs` checks the table, the `Task` column, the specs and the copy of the table in task 0004 against each other.

## Deviations

Each entry states the rule, the reason and the decision of README section 15. The ownership table marks the same rows. A row keeps the status `open` until every task in its `Task` column has added its code and test, and then takes the status `deviation`.

### 5.4.3 Untrusted files scanned for malware

Rule: with `MEDIA_CLAMAV_SOCKET` set, every uploaded and imported media file passes a clamd `INSTREAM` scan before ffprobe, ffmpeg, xmerl or the WebVTT check reads it (only the signature and header check of `Espalier.Media.Sniff`, which reads at most the first 1 MiB in the BEAM, runs before the scan), and a finding, an exceeded scan limit or a failed scan rejects the file (task 0018). Without the setting, no scan runs.

Reason: a scan needs a clamd service with current signatures and the memory for them, which not every installation runs; the compose example of task 0018 provides one. Without it the platform relies on its other controls: only authors with a second factor from the last 10 minutes upload; the signature allowlist admits PNG, JPEG, GIF, WebP, SVG, MP4, Matroska and WebVTT files only; ffmpeg writes every still image, every GIF and APNG and every converted video anew; an animated WebP is written anew in the BEAM without its metadata chunks, while its frame bitstreams pass unchanged into the delivery file and the poster; a remuxed video gets a new WebM container from ffmpeg, while its VP9 and Opus streams pass unchanged; every SVG is rebuilt from an allowlist, and every WebVTT file is checked; no file is executed; and the media route serves files only to signed-in users, with a `sandbox` CSP and `nosniff`. README section 15, decision D19, records the unscanned default as a deviation.

Measured behaviour: the `:clamav` test of `test/espalier/media/clamd_test.exs` runs clamd of the development shell (ClamAV 1.4.6) with the marker signature of `docs/guides/examples/espalier-test.ndb` and an EICAR signature. A clean file answers `:clean`, a WebVTT file whose `NOTE` block holds `ESPALIER-CLAMAV-TEST-MARKER` answers the finding `Espalier.Test.Marker.UNOFFICIAL`, the EICAR file answers `Espalier.Test.Eicar.UNOFFICIAL`, and a file beyond a limit of clamd answers `limits_exceeded` or `size_limit`, which fail the asset with `scan_failed`. The fake server of the same test file gives `scan_failed` with the reason tags `timeout`, `closed`, `connect` and `reply`. With the example `docs/guides/examples/compose.clamav.yaml` (`clamav/clamav:1.5.4`), the service uses 954 to 979 MiB after loading its signatures (up to 1.9 GiB during a reload), it scanned a video of 1024 MiB in up to 73 seconds, and `MaxScanTime` (220000 ms) stops a longer scan with `Heuristics.Limits.Exceeded.MaxScanTime`, which fails the asset with `scan_failed`; a stream above `StreamMaxLength` failed it with `scan_failed` and the reason `closed`, because clamd closed the socket before the client had read its answer `INSTREAM size limit exceeded`. When the client reads that answer before the socket closes, the asset fails with the reason `size_limit`, as in the `:clamav` test for a stream above `StreamMaxLength`; the fake server test accepts both outcomes. Without `MEDIA_CLAMAV_SOCKET`, `Espalier.Media.Clamd.enabled?/0` is false, and the job starts with the detection and the processor of the kind.

### 6.2.8 Passwords verified exactly as received

Rule: every password is normalized to Unicode NFC with `String.normalize(password, :nfc)` in `Espalier.Accounts.PasswordPolicy.prepare/1` before the length check, the blocklist checks, the breached-password check, the Argon2id hash and the verification.

Reason: NIST SP 800-63B-4 section 3.1.1.2 asks verifiers that accept Unicode to apply NFC before hashing, so that verification stays consistent across keyboards and devices that produce different Unicode forms of the same characters. ASVS 6.2.8 asks for verification exactly as received, and README section 15, decision D12, follows NIST.

Directory passwords go to the LDAP server unchanged (task 0007, step 8).

### 6.5.5 Lifetime of out-of-band tokens and TOTP

Rule: TOTP verification accepts the code of the current and of the previous 30-second step (task 0005, step 10), so a code is accepted for up to 60 seconds. Each code works once, because the factor stores the last used step (ASVS 6.5.1).

Reason: RFC 6238 section 5.2 recommends that a verifier accepts at most one past time step as transmission delay, because a code that the app shows at the end of a step reaches the server in the next one. ASVS 6.5.5 limits a TOTP to 30 seconds. README section 6.6 follows RFC 6238, and README section 15, decision D15, records the departure as a deviation.

Invitation, e-mail change and recovery links keep the limit of 10 minutes that the row requires (tasks 0004 and 0005).

### 11.4.1 Only approved hash functions: HMAC-SHA-1 in TOTP

Rule: TOTP codes are HMAC-SHA-1 values with 6 digits and 30-second steps (`nimble_totp`, task 0005, step 10; README section 6.3).

Reason: RFC 6238 builds TOTP on HOTP, which uses HMAC-SHA-1, and names HMAC-SHA-256 and HMAC-SHA-512 as options. The key URI format of Google Authenticator states that "the algorithm parameter is ignored by the Google Authenticator implementations" (retrieved 2026-10-08), so a code computed with another algorithm would fail in those apps. `nimble_totp` 1.0.0 offers no other algorithm either, because its options `:digits` and `:algorithm` exist only on its unreleased master (task 0005, step 10). ASVS Appendix C rates HMAC-SHA-1 as legacy: such a mechanism "might still be used for compatibility", and its use "is currently not considered to be a vulnerability in itself". ASVS 11.4.1 admits approved hash functions only, and README section 15, decision D14, records the use as a deviation. Each code works once, and the durable `:totp` counter limits guessing (ASVS 6.3.1 and 6.5.1).

### 11.4.1 Only approved hash functions: SHA-1 in the range request

Rule: with `PASSWORD_BREACH_CHECK=hibp`, `Espalier.Accounts.BreachedPasswords.check/1` sends the first five hex characters of the SHA-1 hash of the NFC-normalized password to the Pwned Passwords range API and compares the returned suffixes on the server (task 0004).

Reason: the range API accepts a prefix of the SHA-1 hash or of the NTLM hash of the password. NTLM is MD4, which ASVS Appendix C lists as disallowed, so SHA-1 is the only usable format. The platform stores no SHA-1 value, and passwords are stored only as Argon2id hashes (ASVS 11.4.2). The check is off by default (README section 15, decision D10). ASVS Appendix C rates SHA-1 as legacy, and README section 15, decision D14, records the use as a deviation from ASVS 11.4.1.

### 11.6.1 Approved algorithms for key generation and signatures: RS256

Rule: the ID token allowlist holds RS256 next to PS256 and ES256 (task 0006), and passkey registration accepts COSE -257 (RS256) next to -7 and -8 (task 0005). The platform creates no RS256 signature: every `private_key_jwt` client assertion uses PS256, because task 0006 (step 5) sets PS256 as the only signing algorithm of every provider with a client certificate. A provider that accepts no PS256 assertion authenticates the client with a secret (task 0006). The same step switches off the request objects and DPoP proofs that oidcc 3.9.0 would otherwise sign on its own.

Reason: the discovery documents of Google and of Microsoft Entra ID list `RS256` as their only value of `id_token_signing_alg_values_supported` (retrieved 2026-10-08). The FIDO Metadata Service lists the Windows Hello authenticators with RS256 (COSE -257) as their only algorithm, and WebAuthn Level 3 asks relying parties that support a wide range of authenticators to offer -8, -7 and -257. ASVS Appendix C rates RSASSA-PKCS1-v1_5 as disallowed, and README section 15, decision D13, keeps it for the verification of ID tokens and passkey assertions only. The Entra spike of decision D4 (task 0006, step 18) showed on 2026-10-09 that Entra ID accepts PS256 client assertions, so the platform creates no RS256 signature.

### 12.3.1 Encrypted connections to and from the application: the proxy hop

Rule: the reverse proxy example forwards requests to the application over HTTP on the compose network (task 0017, step 3). The connections to SMTP, the directory and PostgreSQL use TLS (tasks 0004, 0007 and 0017).

Reason: the entry for 12.3.3 below gives the reason, because both entries record the same hop (README section 15, decision D17).

### 12.3.3 TLS between internal HTTP services

Rule: the reverse proxy example forwards requests to the application over HTTP on the compose network (task 0017, step 3).

Reason: the proxy and the application run on one host and talk over a Docker network of that host, the compose network of the example or a network that an existing proxy on the host shares with the application, which `self-hosting.md` requires (task 0017), so the hop does not leave the host. The application reaches PostgreSQL through TLS with certificate verification (ASVS 12.3.1). A proxy on another host needs TLS on this hop, which `self-hosting.md` states. README section 15, decision D17, records the hop as a deviation.

### 13.2.1 Backend communication authenticated

Rule: the directory service account authenticates with a password in a simple bind (task 0007).

Reason: `:eldap` offers only `simple_bind`. The mitigations are a dedicated service account that can only read user objects below the base DN (ASVS 13.2.2), the password from the runtime environment (ASVS 13.3.1), TLS on every directory connection outside dev and test (ASVS 12.3.1), and the rotation of that password, which the identity provider guide of task 0007 describes. README section 15, decision D15, records the bind as a deviation.

### 14.2.1 No sensitive data in URLs

Rule: two values of the OIDC flow travel in a query string: the authorization response (`code` and `state`) on the callback, and the intent of task 0006 on `/auth/oidc/<key>?intent=<token>`. E-mail link tokens and the sign-in ticket travel in the URL fragment and in request bodies (task 0011), and the lookups of tasks 0013 and 0015 take the e-mail address in the request body.

Reason: the response mode `query` keeps the callback a GET navigation that carries the `Lax` transaction cookie (task 0006, step 9), and the intent starts the provider flow as a top-level navigation. Task 0006 limits both values: the code works once and is bound to the PKCE verifier, the intent works once, expires after 5 minutes and works only with the session that created it, and `filter_parameters` keeps `code`, `state` and `intent` out of the logs. README section 15, decision D15, records both values as a deviation.
