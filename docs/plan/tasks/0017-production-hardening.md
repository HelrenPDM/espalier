## Goal
A self-hosting organization runs the platform from the published image with one
compose file and a reverse proxy, and configures an identity provider from the
guides. A missing or invalid setting stops the boot with one message that names
every gap. The headers and cookies of 0004 hold on the running container, the
proxy example enforces HSTS and TLS 1.2 or 1.3, the application reaches
PostgreSQL only through verified TLS, the image carries no secret, no
repository metadata and no development feature, dependencies are audited, and
the security and operations settings are documented. The image carries
`LICENSE` and `NOTICE`, as section 4 of the Apache License 2.0 requires for a
redistribution in object form. The content pack guide covers the learning
objectives and the alignment checks that every import runs, so that an author
who follows it writes a pack that passes them. The data protection guide
and the legal assessment belong to the GDPR workstream (README section 10).

## Scope
- In: final Dockerfile and compose file, `LICENSE` and `NOTICE` in the image, TLS between the application and PostgreSQL, boot-time configuration checks, verification of the headers and cookies of 0004 against the running container, the revisit of the `__Host-Http-` cookie prefix, the reverse proxy and log forwarding examples, release functions, smoke test, `make release-push`, the final dependency audit, guides for self-hosting, identity providers, content packs (with the learning objectives and the alignment checks), security and operations.
- Out: Kubernetes manifests, managed hosting, the log storage system and the secrets manager of the operator, the data protection guide and the legal assessment (GDPR workstream, README section 10).

2. Database TLS (12.3.1). In `config/runtime.exs` for `:prod`, replace the commented line `# ssl: true` that `phx.new` 1.8.15 writes into the Repo configuration with `ssl: [verify: :verify_peer, cacertfile: <DATABASE_CA_CERT_FILE>, server_name_indication: String.to_charlist(URI.parse(database_url).host)]`. 3. `compose.yaml` and the proxy example. Keep the services `db` and `app` of 0001, add a volume for `/data/exports`, `EXPORT_DIR=/data/exports` and `restart: unless-stopped`. Write `docs/guides/examples/Caddyfile`:
   ```caddyfile
   {$SITE_ADDRESS} {
   	tls {
   		protocols tls1.2 tls1.3
   	}
   	header Strict-Transport-Security "max-age=63072000; includeSubDomains"
   	@trace method TRACE
   	respond @trace 405
   	reverse_proxy app:4000
   }
   ```
   Write `docs/guides/examples/compose.caddy.yaml`, which adds a `caddy` service (image `caddy:2.11`, check the current tag) with this file, the volume `caddy_data` at `/data` and the published port `${HTTPS_PORT:-443}:443`, and gives `caddy` a fixed address on a network with a fixed subnet, so that `TRUSTED_PROXIES` names it. The Caddy documentation states the behaviour this file relies on: `header` precedes `respond` in the default directive order, so the 405 answer to `TRACE` also carries the HSTS header (Caddyfile directives, section "Directive order"); `protocols` sets the minimum and maximum TLS version, and the defaults are `tls1.2` and `tls1.3` (directive `tls`); `reverse_proxy` ignores the values of incoming `X-Forwarded-*` headers and sends the client address, unless `trusted_proxies` names the sender (directive `reverse_proxy`, section "Defaults"). The acceptance checks each of these on the running example. With `SITE_ADDRESS=localhost`, Caddy issues the certificate from its local CA, whose root lies at `/data/caddy/pki/authorities/local/root.crt` in the container. Write `docs/guides/examples/compose.logging.yaml`, which sets for `app` the `syslog` logging driver with `syslog-address: tcp+tls://<receiver>:6514`, `syslog-tls-ca-cert`, `syslog-format: rfc5424micro` and `tag: espalier`. The Docker documentation of the syslog driver lists the scheme `tcp+tls` and the format `rfc5424micro`, and `ValidateLogOpt` of that driver rejects every other option key with `unknown log opt` (moby, `daemon/logger/syslog/syslog.go`).
   - Cipher suites (ASVS 12.1.2). Check with `nix-shell -p nmap --run "nmap --script ssl-enum-ciphers -p <port> localhost"` against the running example which cipher suites the proxy offers for TLS 1.2 and TLS 1.3, and record the list, the preference order that nmap reports and the date in `security.md` and in row 12.1.2. Every TLS 1.2 suite in the list uses ECDHE key exchange and AES-GCM or ChaCha20-Poly1305. When the defaults of Caddy offer another suite, the `tls` block of the Caddyfile names the allowed suites with its `ciphers` subdirective.
   - `compose.yaml` publishes the port of `app` on the loopback address only (`127.0.0.1:4000:4000`), so that from another host only the proxy reaches the application, and the scripts of steps 5, 6 and 9 still reach it on `http://localhost:4000`.
