## Goal
A self-hosting organization runs the platform from the published image with one
compose file and a reverse proxy, and configures an identity provider from the
guides. A missing or invalid setting stops the boot with one message that names
every gap. The headers and cookies of 0004 hold on the running container, the
proxy example enforces HSTS and TLS 1.2 or 1.3, the application reaches
PostgreSQL only through verified TLS, the image carries no secret, no
repository metadata and no development feature, dependencies are audited, and
the security and operations settings are documented. The image carries
`LICENSE` and `NOTICE`, as section 4 of the Apache License 2.0 requires for a
redistribution in object form. The content pack guide covers the learning
objectives and the alignment checks that every import runs, so that an author
who follows it writes a pack that passes them. The data protection guide
and the legal assessment belong to the GDPR workstream (README section 10).

## Scope
- In: final Dockerfile and compose file, `LICENSE` and `NOTICE` in the image, TLS between the application and PostgreSQL, boot-time configuration checks, verification of the headers and cookies of 0004 against the running container, the revisit of the `__Host-Http-` cookie prefix, the reverse proxy and log forwarding examples, release functions, smoke test, `make release-push`, the final dependency audit, guides for self-hosting, identity providers, content packs (with the learning objectives and the alignment checks), security and operations.
- Out: Kubernetes manifests, managed hosting, the log storage system and the secrets manager of the operator, the data protection guide and the legal assessment (GDPR workstream, README section 10).

2. Database TLS (12.3.1). In `config/runtime.exs` for `:prod`, replace the commented line `# ssl: true` that `phx.new` 1.8.15 writes into the Repo configuration with `ssl: [verify: :verify_peer, cacertfile: <DATABASE_CA_CERT_FILE>, server_name_indication: String.to_charlist(URI.parse(database_url).host)]`. Since Postgrex 0.18.0, `ssl: true` emits a warning, because that setting runs no server certificate verification (Postgrex CHANGELOG, v0.18.0). Add `DATABASE_CA_CERT_FILE` with a comment to `.env.example`. In `compose.yaml`:
   - A one-shot service `db-certs` runs the `postgres:18` image as root. On its first run it generates with `openssl` a CA and a server certificate for the host name `db` (subject alternative name `DNS:db`), both with EC P-256 keys, SHA-256 signatures and a validity of 825 days. It deletes the CA key, writes `server.pem` and `server.key` (owner 999, the `postgres` user of the image, mode 600) and a `pg_hba.conf` with the lines `local all all trust` and `hostssl all all all scram-sha-256` into the volume `db-tls`, and writes `ca.pem` into the volume `db-ca`. Check with `docker run --rm --entrypoint openssl postgres:18 version` that the image contains the `openssl` binary.
   - `db` depends on `db-certs` with `service_completed_successfully`, mounts `db-tls` read-only and starts with `-c ssl=on -c ssl_cert_file=... -c ssl_key_file=... -c ssl_min_protocol_version=TLSv1.2 -c hba_file=...`. With that `pg_hba.conf`, a TCP connection without TLS fails with `no pg_hba.conf entry ... no encryption`, and the image's first-run initialization keeps working over the local socket.
   - `app` mounts `db-ca` read-only and sets `DATABASE_CA_CERT_FILE` to its `ca.pem`.
   - `docs/security/key-management.md` states the validity of the generated certificates and their renewal (step 13), and `operations.md` links to that section. For an external PostgreSQL, `self-hosting.md` sets `DATABASE_URL` and `DATABASE_CA_CERT_FILE` to the values of that server.
3. `compose.yaml` and the proxy example. Keep the services `db` and `app` of 0001, add a volume for `/data/exports`, `EXPORT_DIR=/data/exports` and `restart: unless-stopped`. Write `docs/guides/examples/Caddyfile`:
   ```caddyfile
   {$SITE_ADDRESS} {
   	tls {
   		protocols tls1.2 tls1.3
   	}
   	header Strict-Transport-Security "max-age=63072000; includeSubDomains"
   	@trace method TRACE
   	respond @trace 405
   	reverse_proxy app:4000
   }
   ```
   Write `docs/guides/examples/compose.caddy.yaml`, which adds a `caddy` service (image `caddy:2.11`, check the current tag) with this file, the volume `caddy_data` at `/data` and the published port `${HTTPS_PORT:-443}:443`, and gives `caddy` a fixed address on a network with a fixed subnet, so that `TRUSTED_PROXIES` names it. The Caddy documentation states the behaviour this file relies on: `header` precedes `respond` in the default directive order, so the 405 answer to `TRACE` also carries the HSTS header (Caddyfile directives, section "Directive order"); `protocols` sets the minimum and maximum TLS version, and the defaults are `tls1.2` and `tls1.3` (directive `tls`); `reverse_proxy` ignores the values of incoming `X-Forwarded-*` headers and sends the client address, unless `trusted_proxies` names the sender (directive `reverse_proxy`, section "Defaults"). The acceptance checks each of these on the running example. With `SITE_ADDRESS=localhost`, Caddy issues the certificate from its local CA, whose root lies at `/data/caddy/pki/authorities/local/root.crt` in the container. Write `docs/guides/examples/compose.logging.yaml`, which sets for `app` the `syslog` logging driver with `syslog-address: tcp+tls://<receiver>:6514`, `syslog-tls-ca-cert`, `syslog-format: rfc5424micro` and `tag: espalier`. The Docker documentation of the syslog driver lists the scheme `tcp+tls` and the format `rfc5424micro`, and `ValidateLogOpt` of that driver rejects every other option key with `unknown log opt` (moby, `daemon/logger/syslog/syslog.go`).

## Notes
- The image contains no content pack besides the demo pack. Organizations import their own packs after deployment.
- Keep `AUTH_DEMO` off in every example except `.env.demo.example` and the smoke test that reads it.
- This task creates no table, no protected column and no route. It registers no schema under `Espalier.Crypto.Rotation`, adds no row to the section "Columns" of `docs/security/crypto-inventory.md` and adds no OpenAPI operation. Its inventory rows are the keys and certificates of step 13.
- The data protection guide for operators (what each table stores, retention, the limits of anonymity, what a SCORM export sends to the receiving LMS) is part of the GDPR workstream (README section 10).
- The hop from the reverse proxy to the application runs over the compose network on the same host. The notes of row 12.3.1 state this, and `self-hosting.md` requires the proxy and the application on one host.
- RFC 10017, section 6.1.3.2, recommends a cookie name prefix such as `__Host-Http-`, which comes from draft-ietf-httpbis-layered-cookies. The browser support figures in step 7 come from caniuse, retrieved 2026-10-07.
- `mix hex.audit` reports advisories and honors `ignore_advisories` and the `HEX_IGNORE_ADVISORIES` environment variable from Hex 2.5.1 (released 2026-07-09; README section 13).
- Step 3 targets Caddy 2.11.7 (image `caddy:2.11`) and cites the Caddy documentation for the directives `header`, `respond`, `tls` and `reverse_proxy`. Step 2 targets the `postgres:18` image (PostgreSQL 18.6 on Debian trixie, whose `openssl` package provides OpenSSL 3.5.7).
- The runner stage of `phx.gen.release` installs `openssl` and `ca-certificates` and sets `USER nobody`; it has no `HEALTHCHECK`, no `EXPOSE` and no copy of `LICENSE` or `NOTICE` (Phoenix 1.8.15, `priv/templates/phx.gen.release/Dockerfile.eex`), which step 1 adds. The `.dockerignore` of the same release follows the line `.git` with `!.git/HEAD` and `!.git/refs` (`priv/templates/phx.gen.release/dockerignore.eex`), which step 1 removes.
- The published image redistributes the work in object form, so section 4 of the Apache License 2.0 applies to it (0002 Notes).
