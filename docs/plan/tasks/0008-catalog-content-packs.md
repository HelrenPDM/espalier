## Goal
The catalog tables exist as modeled, a content pack directory can be validated,
stored as a draft and published into the live tables, and the repository ships
a neutral demo pack that exercises every block kind, item kind and requirement
kind. Every module of a pack declares learning objectives in the four
competence areas (subject, method, self and social), each with a depth and a
phase. The importer checks the constructive alignment of README domain rule 14:
every objective has a teaching lesson and evidence, every item that counts for
a credential provides evidence for an objective, every module covers the four
areas or names the place where a missing area is covered, and the kind of
evidence fits the depth. `mix espalier.alignment` prints the alignment matrix of
a pack, and the demo pack passes the check in strict mode.

## Steps
1. Add `{:yaml_elixir, "~> 2.12"}` to `deps` in `mix.exs` and run `nix-shell --run "mix deps.get"`. Check with `nix-shell --run "mix hex.info yaml_elixir"` that 2.12 is the current minor. On 2026-10-07, hex.pm listed 2.12.2 (published 2026-05-30, so more than seven days old, as the cooldown of README section 13 requires) with the single dependency `yamerl ~> 0.10`, and the OSV database listed no advisory for either package. `mix.lock` then holds `yaml_elixir` and `yamerl`.
2. Generate the catalog in the order below, one command after another, so that each migration gets its own timestamp and every referenced table exists first. Every command carries `--no-scope` (README section 5): the catalog holds no person-linked rows, and once 0004 has registered its default scope in `config/config.exs`, the generators add a `user_id` column to every table generated without that flag (Phoenix 1.8.15, `lib/mix/phoenix/scope.ex` and `priv/templates/phx.gen.schema/migration.exs.eex`). Use `mix phx.gen.context Catalog Program programs ... --no-scope` for `Program` and `mix phx.gen.schema Catalog.<Name> <table> ... --no-scope` for the rest. With the project default `--binary-id` of 0001, every generated schema has a `:binary_id` primary key, and every `references` column has the type `:binary_id`. Arrays of enums (`phases` and `collapsed_on`) are generated as `array:string`; change the schema field to `{:array, Ecto.Enum}` with the values from `domain-values.puml`, and keep the migration column `{:array, :string}`.

   - `Catalog.Source sources program_id:references:programs key:string title:string publisher:string url:string edition_date:date retrieved_on:date kind:enum:law:guidance:vendor:study:press:other`
   - `Catalog.GlossaryTerm glossary_terms program_id:references:programs slug:string label:string short_text:text`
   - `Catalog.Segment segments program_id:references:programs key:string label:string description:text default_path:enum:short:full position:integer`
   - `Catalog.Module modules program_id:references:programs number:integer title:string summary:text phases:array:string domains:array:string single_path:boolean refresher_unit:boolean areas_elsewhere:map`. The schema field `areas_elsewhere` gets `default: %{}`.
   - `Catalog.Lesson lessons module_id:references:modules key:string position:integer title:string`
   - `Catalog.LearningObjective learning_objectives program_id:references:programs module_id:references:modules key:string statement:text area:enum:subject:method:self:social depth:enum:know:apply:judge phase:enum:orient:understand:apply:anchor:update domain:string position:integer`. The three enum fields carry the values of `CompetenceArea`, `Depth` and `Phase` in `domain-values.puml`. `domain` stays nullable.
   - `Catalog.Block blocks lesson_id:references:lessons position:integer kind:enum:text:explanation:example:case_comparison:quote:callout:placeholder body:text provenance:enum:invented:sourced:vendor_statement:assumption:placeholder collapsed_on:array:string placeholder_key:string`

   - `Catalog.Item items program_id:references:programs module_id:references:modules lesson_id:references:lessons key:string kind:enum:single_choice:multiple_choice:slot_builder:classification:checklist_drill:poll stem:text core:boolean phase:enum:orient:understand:apply:anchor:update provenance:enum:invented:sourced:vendor_statement:assumption:placeholder config:map position:integer`. An item has no area and no depth of its own; it reaches both through the objectives it names (step 3).
   - `Catalog.Option options item_id:references:items key:string label:text correct:boolean feedback:text position:integer`
   - `Catalog.Station stations program_id:references:programs module_id:references:modules position:integer kind:enum:self_assessment:overview:module:credential:companion_formats:feedback title:string config:map`
   - `Catalog.Qualification qualifications program_id:references:programs code:string title:string audience:text unlocks:array:string add_on:boolean validity_kind:enum:none:months:event validity_months:integer refresher_mode:enum:update_unit:full_run:test_only phases:array:string`
   - `Catalog.Requirement requirements qualification_id:references:qualifications kind:enum:module_completed:assessment_passed:policy_acknowledged:attendance:qualification_held target_key:string`
   - `Catalog.CompanionFormat companion_formats program_id:references:programs key:string title:string description:text phases:array:string attendance_counts:boolean position:integer`

It holds the id of the importing user, or `NULL` for the mix tasks and the release function, and the catalog tables keep no reference to the `users` table of 0004.
3. Write the join-table migrations with `mix ecto.gen.migration`, one command per table after the generators of step 2 (for example `nix-shell --run "mix ecto.gen.migration create_objective_lessons"`), and the matching `many_to_many` associations:
   - `item_rules (item_id, rule_id)`, `item_reveals (item_id, lesson_id)`, `assessment_items (assessment_id, item_id, position)` with a join schema `Espalier.Catalog.AssessmentItem` for the position, and `qualification_prerequisites (qualification_id, prerequisite_id)`.
   - For the alignment: `objective_lessons (learning_objective_id, lesson_id)`, `item_objectives (item_id, learning_objective_id)` and `format_objectives (companion_format_id, learning_objective_id)`. The associations are `many_to_many :lessons`, `many_to_many :items` (through `item_objectives`) and `many_to_many :companion_formats` (through `format_objectives`) on `LearningObjective`, and `many_to_many :objectives` on `Item` and on `CompanionFormat`. Ecto derives the default join keys from the last part of the schema module name (`association_key/2` in `lib/ecto/association.ex`), which gives `learning_objective_id`, `item_id`, `lesson_id` and `companion_format_id` and matches these columns.
   - `mix ecto.gen.migration` writes an empty migration and adds no scope column, so it takes no `--no-scope`. Each join table is created with `primary_key: false`. Both references use `type: :binary_id`, `null: false` and `on_delete: :delete_all`. Each pair has a unique index, and the second column has an index of its own, so that a lookup from either side uses an index.
4. Edit the generated migrations:
   - Unique indexes for every upsert key: `programs.slug`; `(program_id, key)` for sources, segments, companion formats, items, assessments and learning objectives; `(program_id, slug)` for glossary terms; `(program_id, number)` for modules; `(module_id, key)` for lessons; `(module_id, number)` for rules; `(program_id, code)` for qualifications.
   - `archived_at :utc_datetime` on every keyed table: modules, lessons, learning objectives, rules, items, assessments, qualifications, companion formats, sources, glossary terms and segments.
   - A check constraint on `citations`: `num_nonnulls(block_id, rule_id, item_id) = 1`.
   - `on_delete: :delete_all` on the parent references of blocks (lesson), options (item), citations (block, rule, item), requirements (qualification) and stations (program).
   - `null: false` on every parent reference and key column, except `items.lesson_id` (exam items have no lesson), `stations.module_id`, and the three parent references of `citations`, which the check constraint covers. `learning_objectives` also gets `null: false` on `statement`, `area`, `depth` and `phase`, and `modules.areas_elsewhere` gets `null: false`; the schema default `%{}` and the publisher of step 10 always write a map.
5. The pack format follows the layout of README section 11. Positions follow the order of the entries in a file, except for lessons, which carry `position` in their front matter. Keys and slugs match `^[a-z0-9][a-z0-9-]*$`. `cite` is a list of `source-key#locator` strings.
   - `pack.yaml`: `schema` (integer, 1), `key` (becomes `programs.slug`), `title`, `locale`, `license` (SPDX identifier), `version` (becomes `programs.pack_version`) and `alignment` (optional, `strict` or `warn`, default `strict`). `alignment` decides whether checks 1 to 3 of step 13 report errors or warnings.
   - `sources.yaml`: entries with `key`, `title`, `publisher`, `url` (optional), `edition_date`, `retrieved_on` and `kind`.
   - `glossary.yaml`: entries with `slug`, `label` and `short_text`.
   - `segments.yaml`: entries with `key`, `label`, `description` and `default_path`.
   - `stations.yaml`: entries with `kind`, `title`, `module` (the module number, kind `module` only) and `config`. The `self_assessment` station holds `question` in `config`, where 0014 reads it; the `overview`, `credential` and `companion_formats` stations hold `intro`.
   - `feedback.yaml`: `intro` and `questions`, each question with `key`, `kind` (`single_choice`, `scale` for the values 1 to 5, or `free_text`), `label` and, for `single_choice`, `options` with `key` and `label`. The loader stores `intro` and `questions` in the `config` of the `feedback` station, where 0014 reads the questions.
   - `qualifications.yaml`: entries with `code`, `title`, `audience`, `unlocks`, `add_on`, `validity_kind`, `validity_months`, `refresher_mode`, `phases` and `requirements`, each requirement with `kind` and `target`. The target is the module number for `module_completed`, the assessment key for `assessment_passed`, the policy key for `policy_acknowledged`, the format key for `attendance` and the qualification code for `qualification_held`. It is stored as a string in `requirements.target_key`.
   - `formats.yaml`: entries with `key`, `title`, `description`, `phases`, `attendance_counts` and `objectives` (optional, objective keys of the pack that the format anchors or provides evidence for).
   - `modules/<directory>/module.yaml`: `number`, `title`, `summary`, `phases`, `domains`, `single_path`, `refresher_unit` and `areas_elsewhere` (optional). `areas_elsewhere` maps a competence area (`subject`, `method`, `self` or `social`) to a map with `where` and `reason`. `where` is `format:<format key>` or `module:<module number>`, and `reason` is a text that states what the named place covers.
   - `modules/<directory>/objectives.yaml` (optional): entries with `key`, `statement` (a sentence of the form "Learners can ..."), `area` (`subject`, `method`, `self` or `social`), `depth` (`know`, `apply` or `judge`), `phase` (`orient`, `understand`, `apply`, `anchor` or `update`), `domain` (optional, one of the module's `domains`) and `taught_in` (lesson keys of the module). A module without this file has no objectives, and check 3 of step 13 then reports every area that `areas_elsewhere` does not name.
   - `modules/<directory>/rules.yaml`: entries with `number`, `statement`, `action` and an optional `cite`.
   - `modules/<directory>/items.yaml`: entries with `key`, `kind`, `lesson` (a lesson key of the module, for practice items), `stem`, `core`, `phase`, `provenance`, `objectives` (optional, objective keys of the pack), `rules` (rule numbers of the module), `reveals` (lesson keys of the module), an optional `cite`, `options` for `single_choice`, `multiple_choice` and `poll` (each option with `key`, `label`, `correct` and `feedback`), and `config` for the other kinds. A `slot_builder` config has `slots`, each with `key`, `label` and `options` (`key`, `label`, `correct`, `feedback`). A `classification` config has `categories` (`key`, `label`), `cases` (`key`, `text`, `feedback`) and `expected` (case key to category key). A `checklist_drill` config has `checks` (`key`, `label`, `required`); its answer always includes initials (0009 step 10). Exam items are entries of this file as well, so practice items and exam items name their objectives here.
   - `modules/<directory>/assessment.yaml` (optional): entries with `key`, `title`, `kind`, `counts_for_credential`, `max_wrong`, `core_required` and `items` (item keys of the module in order). The objectives of an exam item come from its entry in `items.yaml`.
   - `modules/<directory>/lessons/*.md`: YAML front matter with `title` and `position`, then the body. The file name without `.md` is the lesson key.
6. `Espalier.Catalog.Pack.Loader.load(path)` returns `{:ok, map}` or `{:error, errors}`. It walks the directory with `File.lstat/1`, rejects every symbolic link and every entry that is neither a directory nor a regular file, and reads only the files of step 5, `objectives.yaml` included, so that no read leaves `path`. Each YAML file and each lesson front matter is read as text and parsed in two passes:
   - `Espalier.Catalog.Pack.LineIndex.build(text)` starts the `yamerl` application, calls `:yamerl_constr.string(text, detailed_constr: true, str_node_as_binary: true)` and maps the path of every node, for example `["items", 2, "options", 0]`, to its line. yamerl 0.10.0 stores the location of each node as `[{line, L}, {column, C}]` (`src/yamerl_constr.erl`). The walk stops with an error after 50,000 nodes, which bounds the expansion of YAML aliases.
   - When the walk succeeds, `YamlElixir.read_from_string/2` without the option `atoms: true` returns the data with string keys. yaml_elixir 2.12.2 converts keys of the form `:name` with `String.to_atom/1` only under that option (`lib/yaml_elixir/mapper.ex`), so a pack creates no atoms.
   A parse error arrives as `YamlElixir.ParsingError` with `line` and `column` (`lib/yaml_elixir/exceptions.ex`) and is reported with the file name. A lesson file is split at its `---` delimiters, and the body goes to step 7 with the line number of its first line.
7. `Espalier.Catalog.Pack.Directives.split(markdown, first_line)` splits a lesson body into blocks. A line matching `^:::([a-z_]+)(\{.*\})?\s*$` opens a block, and a line matching `^:::\s*$` closes it. Attributes are `key=value` or `key="value with spaces"`, separated by spaces. The attributes are `provenance`, `collapsed_on` (comma-separated paths), `cite` (`source-key#locator`, several separated by commas) and, for `placeholder`, `key`, which becomes `placeholder_key`. Every block carries `provenance`, except `placeholder`, whose provenance is `placeholder` (README principle 4). The lines between the opening and the closing line become `body`, and the order of the blocks becomes `position`. Each of the following is an error with its line number: an unknown kind, an unknown attribute, a missing `provenance`, an opening line inside an open block, an unclosed block, and non-blank text outside a block.
8. `Espalier.Catalog.Pack.Validator.validate(map)` checks the loaded map with embedded Ecto schemas, one per file type, and returns `{errors, warnings}`: two lists of maps, each with `file` (the path of the file relative to the pack directory, for example `modules/01-basics/items.yaml`), `line` (from the line index, the YAML parser or the directive splitter) and `message`. An entry that comes from `Alignment.check/1` also carries `check`, `module` and `key` (last bullet of this step). Only the alignment checks of step 13 produce warnings; every other check of this step reports an error in both alignment modes. It checks:
   - `schema` equals 1. Any other value is an error whose message names the supported schema versions (README section 16).
   - Keys, slugs, numbers and codes are unique in their scope: item keys, assessment keys and objective keys in the pack, because they become `(program_id, key)`; lesson keys and rule numbers in their module; all others in their file.
   - References resolve: `rules` and `reveals` to rules and lessons of the same module, every `cite` to a source key, every `[[term:slug]]` and `[[term:slug|label]]` in a Markdown field to a glossary slug, a station `module` to a module number, assessment `items` to items of the same module, and requirement targets to a module, to an assessment of kind `exam`, to a format with `attendance_counts: true` or to a qualification of the pack. `qualification_held` requirements form no cycle.
   - Objective references resolve: every `taught_in` entry to a lesson of the objective's module, the `objectives` of items and formats to objective keys of the pack, and an objective `domain` to an entry of the module's `domains`. An item can name an objective of another module, because objective keys are unique in the pack.
   - `areas_elsewhere` is well formed: every key is one of the four areas, every `reason` is a non-empty text, and every `where` matches `^format:[a-z0-9][a-z0-9-]*$` with a format key of the pack or `^module:[1-9][0-9]*$` with the number of another module of the pack. A module that names its own number is an error.
   - Placeholder keys and `policy_acknowledged` targets match the key format. Policies live in the Policies context of 0013, and a placeholder block without a policy version shows its own text (README section 7, rule 8), so the validator resolves neither.
   - Item kinds carry what they need. `single_choice` has at least two options and exactly one correct option; `multiple_choice` has at least two options and at least one correct option; `poll` has at least two options and no correct option; every slot of `slot_builder` has at least two options and at least one correct option; `classification` maps every case to a known category in `expected`; `checklist_drill` has at least one required check.
   - Every item names a lesson or is listed by an assessment, and an item listed by an exam names no lesson. An exam has at least one item, a `max_wrong` from 0 to the number of its items minus one, and at least one core item when `core_required` is true.
   - Every source has `edition_date` and `retrieved_on` (README principle 4), and every `quote` block cites at least one source.
   - `validity_kind: months` needs `validity_months` above 0, `months` and `event` need a `refresher_mode`, and `update_unit` needs a module with `refresher_unit: true`.
   - The pack has exactly one `self_assessment` station when `segments.yaml` has entries and exactly one `feedback` station when `feedback.yaml` exists.
   - Constructive alignment. When the checks above report no error, the validator calls `Espalier.Catalog.Alignment.check/1` (step 13) with the loaded data in the shape of the normalized map of step 9 and adds the findings to its errors and warnings. Running the alignment checks after the reference checks means that every key they follow resolves. The validator places each finding in the directory of the module that the finding names: a finding on an objective or an item at the line of the entry with that key in `objectives.yaml` or `items.yaml`, and a finding on a module area at the line of that area in `areas_elsewhere` of `module.yaml`, or at line 1 of `module.yaml` when `areas_elsewhere` does not name the area. Each such entry keeps `check`, `module`, `key` and `message` of the finding, and its `file` is the path in the pack, for example `modules/01-basics/items.yaml` for the finding with the file `items.yaml` in module 1. The members `check` and `key` let the packs page of 0015 separate the alignment entries from the other entries of the report.
9. `Espalier.Catalog.Pack.Importer.import(path, actor_id)` runs loader and validator and inserts a `PackImport` with `pack_key`, `pack_version` and `imported_by_id` (`actor_id`). Without errors, the status is `validated` and `payload` holds the normalized map; with errors, the status is `failed` and `payload` stays empty. In both cases `report` holds `errors` and `warnings`, the two lists of the validator of step 8 with every member of their entries: `file`, `line` and `message` for each entry, and `check`, `module` and `key` in addition for each entry of the alignment checks. The warnings of a validated import thus reach the packs page of 0015, and that page selects the alignment entries by `check`. `report` is a `:map` column, so an entry read back from the database has string keys. `pack_key` and `pack_version` stay empty when `pack.yaml` cannot be read. The normalized map holds the `alignment` value of `pack.yaml` (with the default filled in), the `areas_elsewhere` of every module, the objectives of every module with their `taught_in`, and the `objectives` of every item and format. The upload of 0015 calls this function with the id of the signed-in author. The normalized map has string keys and holds no line numbers. Two imports of equal content produce equal payloads, and `Espalier.Interop.Payload.build/1` of 0016 step 1 builds the same map from the live rows of a published program, which 0016 compares in its round-trip test. The importer and `Payload.build/1` share these rules for the shape of the map:
   - Values: every value is a JSON value, so a payload read back from the `:map` column equals the map before the insert. Enum values are strings, dates are ISO 8601 strings such as `2026-05-30`, and a requirement target is the string that `requirements.target_key` stores.
   - Absent fields: every field of an entry of step 5 is present in the map, also when the file leaves it out. An absent scalar is the key with `nil`, so an objective without `domain` holds `"domain" => nil`, a source without `url` holds `"url" => nil` and an exam item holds `"lesson" => nil`. An absent list is `[]` (for example `objectives`, `rules`, `reveals`, `cite`, `taught_in` and `options`), an absent map is `%{}` (`areas_elsewhere` and `config`), and `alignment` holds `strict` when `pack.yaml` names none. A module without `objectives.yaml` holds an empty list of objectives.
   - Order of positioned lists: a list whose rows carry a position or a number keeps that order. Modules follow their `number`, lessons their `position` and rules their `number`. Segments, stations, objectives, items, options, blocks, companion formats and the items of an assessment follow the order of their file. The array fields `phases`, `domains`, `unlocks` and `collapsed_on` keep the order of the file, because their columns store it.
   - Order of the other lists: a list whose table or join table holds no position is sorted in ascending order. The `rules` of an item are sorted by rule number and its `reveals` by lesson key. The `objectives` of an item and of a format and the `taught_in` of an objective are sorted by key, and every `cite` list by its `source-key#locator` strings. Sources and assessments are sorted by key, glossary terms by slug, qualifications by code, and the requirements of a qualification by `kind` and then by `target`. The importer sorts these lists, so an item with `rules: [3, 1]` gives the same payload as an item with `rules: [1, 3]`.
