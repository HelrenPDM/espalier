## Goal
People sign in with Microsoft Entra ID, Google Workspace or any standards-compliant
OIDC provider that the operator configures through environment variables. oidcc
validates the ID token, provider rules check tenant, hosted domain and group
overage, and the account context finds the user by issuer and subject. The flow
ends in the same-origin finish step, which leads to a pending second factor, a
factor enrollment or a full session according to the provider's MFA mode and the
`amr` claim. Signed-in users link a provider after a recent second factor, from
the browser session of the account they link. Federated users in `idp_trusted`
mode step up at the provider, and logout reaches the provider where it offers
RP-initiated or front-channel logout. A mock provider in `test/support/dev_oidc/`
exercises every path in development and tests without network access.

## Security requirements
The ownership table of 0004 step 42 names this task as owner of these rows of `docs/security/asvs-l2.md`, and the section lists exactly the rows whose `Task` column names this task (README section 15, decision D16):

- 1.3.6 (extended by 0013): Every endpoint host of a discovery document, the endpoint of pushed authorization requests included, passes the host allowlist of the provider (`check_endpoints/2`, step 5) before a redirect to the provider or a token request.
- 3.7.2: Redirects leave the application only to the authorization and end-session endpoints of a configured provider whose hosts pass the allowlist of step 5, and no request parameter chooses a redirect target.
- 6.8.1: An external identity is keyed by issuer, tenant and subject, so one provider cannot assert an identity of another, and a link joins only the account whose session started and finished the flow.
- 6.8.2: Every ID token signature is validated against keys of the configured issuer, and an unsigned ID token fails the sign-in.
- 6.8.4: In `idp_trusted` mode, an `amr` claim without a configured multi-factor value leads to the local second factor at sign-in and fails a step-up. A missing `amr` falls back to the operator's `idp_trusted` statement (README section 6.2, rule 4). `auth_time` is checked after a step-up.
- 7.1.3 and 7.6.1: The guide documents how platform sessions relate to provider sessions (front-channel logout, RP-initiated logout, no back-channel logout, step-up with `max_age=0`), and tests cover both logout paths and the step-up.
- 9.1.1, 9.1.2 and 9.1.3: ID tokens are used only after signature validation with the algorithm allowlist RS256, PS256 and ES256 and with keys from the configured issuer's JWKS. RS256 stays, because Google and Entra ID sign ID tokens with RS256 only (README section 15, decision D13).
- 9.2.1, 9.2.2 and 9.2.3: `exp` and `aud` are checked, and only the ID token proves the authentication.
- 9.2.4: The `private_key_jwt` client assertions carry the audience that their provider accepts, the issuer by default or the token endpoint after step 19 (README section 15, decision D4).
- 10.1.1: Provider tokens never leave the backend and are dropped in the callback.
- 10.1.2: State, nonce and PKCE verifier are transaction-specific and bound to the browser through the transaction cookie, the sign-in ticket is bound to the same cookie, and link and step-up intents are bound to the session that created them.
- 10.2.1: Every authorization request carries PKCE S256 and `state`.
- 10.2.2: Each provider has its own redirect URI, the callback rejects a transaction that started at another provider, and the RFC 9207 `iss` parameter is required where the provider advertises it.
- 10.5.1: The nonce of every ID token is checked.
- 10.5.2: The subject comes from `oid` for Entra ID and from `sub` otherwise.
- 10.5.3: A discovery document whose issuer differs from the configured issuer is rejected.
- 10.5.4: `aud` must equal the client id, with no further trusted audience.
- 10.5.5: The requirement does not apply, because the platform offers no back-channel logout. Neither oidcc 3.9.0 nor Entra ID supports it (README section 6.7), and step 22 records the row as `not applicable` with this reason.
- 12.3.2: Discovery, JWKS, token and pushed authorization requests validate the provider's TLS certificate.
- 13.2.4 and 13.2.5: Each provider has an allowlist of endpoint hosts (`AUTH_<KEY>_ALLOWED_HOSTS`, default the issuer host). A configuration that names an authorization, token, JWKS or end-session endpoint on another host fails closed before any token request or redirect, and the guide lists the hosts per provider for an egress allowlist at the network layer.
- 16.5.2: An unreachable provider ends only its own sign-ins with `oidc_unavailable`. The worker keeps retrying with backoff, and local sign-in, the other providers and existing sessions keep working.

1. **Dependencies.** Add these entries to `deps` in `mix.exs` and run `make init`:

Hex has not retired those versions, so the retirement check of `mix hex.audit` does not flag them. Whether the advisory check of Hex 2.5.1 flags CVE-2026-75759 is unverified. The direct requirement `{:oidcc, "~> 3.9"}` keeps vulnerable versions out of the lock in either case. `jose` is listed because application code and the mock call it. `mix deps` must show oidcc 3.9.0 or later, oidcc_plug 0.5.1 or later and jose 1.11.12 or later, and `mix hex.audit` and `mix deps.audit` must pass.

4. **Client keys.** Write `Espalier.Identity.Oidc.ClientKey.load!(cert_file, key_file, kid_format)`, which returns `%{jwk: jwk, kid: kid}` and raises `Espalier.Identity.ConfigError` on any problem.
   - It reads the certificate with `[{:Certificate, der, :not_encrypted}] = :public_key.pem_decode(pem)` and the key with `JOSE.JWK.from_pem/1`. The key must be RSA, and `JOSE.JWK.thumbprint/1` of its public part must equal the thumbprint of the certificate's public key.
   - `kid` is `Base.url_encode64(:crypto.hash(:sha256, der), padding: false)` for `x5t_s256`, `Base.url_encode64(:crypto.hash(:sha, der), padding: false)` for `x5t`, and `Base.encode16(:crypto.hash(:sha, der))` for `sha1_hex`.
   - The JWK becomes `JOSE.JWK.merge(jwk, %{"kid" => kid})`. `oidcc_jwt_util:sign/4` copies only `kid` from the JWK fields into the assertion header.

5. **Provider workers.** Write `Espalier.Identity.Oidc.Supervisor` (`Supervisor`, `:one_for_one`). `start_link(opts)` registers the supervisor with `name: __MODULE__`, and `init(opts)` takes the providers from `Keyword.get(opts, :providers, Espalier.Identity.oidc_providers())`. `Espalier.Application` starts it after the Repo and the vault and before the endpoint when `oidc_env(:start_supervisor, true)` is true. `config/test.exs` sets `start_supervisor: false`, and the OIDC tests start the supervisor themselves (step 17), so neither the supervisor name nor the worker names clash with processes started at boot. `oidc_env/2` reads a key of `Application.get_env(:espalier, Espalier.Identity.Oidc, [])` with a default. `init/1` loads the client keys of step 4 into `:persistent_term`, logs a warning for every provider with `mfa: :idp_trusted` (README section 6.2, rule 4), and starts one worker per OIDC provider:
   ```elixir
   Supervisor.child_spec(
     {Oidcc.ProviderConfiguration.Worker,
      %{
        issuer: provider.issuer,
        name: provider.worker,
        backoff_type: :random_exponential,
        backoff_min: oidc_env(:backoff_min, 1_000),
        backoff_max: oidc_env(:backoff_max, 30_000),
        provider_configuration_opts: %{
          quirks: Espalier.Identity.Oidc.quirks(provider),
          request_opts: Espalier.Identity.Oidc.request_opts()
        }
      }},
     id: provider.worker
   )
   ```
   - The name is a module atom, because the worker's ETS read path works only with a local name. The default `backoff_type` is `:stop`, which ends the worker at the first failed load. `:random_exponential` keeps retrying.
   - `Espalier.Identity.Oidc.quirks/1` returns `document_overrides` with binary keys. Every provider gets `"id_token_signing_alg_values_supported" => ["RS256", "PS256", "ES256"]`, `"request_parameter_supported" => false` and `"dpop_signing_alg_values_supported" => []`. The last two keep oidcc from signing request objects and DPoP proofs with the client key or the client secret (Notes). `entra` adds `"code_challenge_methods_supported" => ["S256"]`, and every provider with a client certificate (`entra`, and `oidc` with `private_key_jwt`) gets `"token_endpoint_auth_signing_alg_values_supported" => ["PS256"]`. Without the PKCE override, oidcc leaves PKCE out of the request without a warning. 10. **Callback.** `EspalierWeb.OidcController.callback/2` runs these checks in this order:
    - The bucket `oidc_callback` allows 30 requests per minute per IP.
    - When the query carries `error`, the action drops the transaction session and redirects to `/auth/finish?error=oidc_cancelled` for `access_denied` and to `/auth/finish?error=oidc_failed` for any other value.
    - The action reads the provider configuration with `:oidcc_provider_configuration_worker.get_provider_configuration(provider.worker)`. The Erlang function returns `:undefined` while the worker has no configuration loaded, for example during backoff right after boot. In that case the action drops the transaction session, logs `authn_login_fail` with the reason `:provider_not_ready`, and redirects to `/auth/finish?error=oidc_unavailable`. A loaded record becomes a struct with `Oidcc.ProviderConfiguration.record_to_struct/1`. The Elixir function `Oidcc.ProviderConfiguration.Worker.get_provider_configuration/1` passes `:undefined` to that conversion, which raises, so the action does not call it.
    - `check_endpoints/2` (step 5) must pass for the loaded configuration. Otherwise the action drops the transaction session, logs `authn_login_fail` with the reason `:endpoint_not_allowed`, and redirects to `/auth/finish?error=oidc_unavailable` before any token request.
    - The transaction session must hold the `"oidc"` map, and its `"provider_key"` must equal the `:provider` path segment. Otherwise the action fails with `oidc_failed` and the reason `:missing_transaction` or `:provider_mismatch`. For providers without RFC 9207, this comparison is the check that RFC 9700 section 4.4.2.2 requires for distinct redirect URIs: a response that arrives at the redirect URI of another provider ends the flow before any token request.
    - When the configuration has `authorization_response_iss_parameter_supported: true`, the query must carry `iss` equal to `provider.issuer`. oidcc_plug 0.5.1 runs its own `iss` check only for such providers. The own check also rejects a missing parameter.
    - The action then calls `Oidcc.Plug.AuthorizationCallback.call(conn, Oidcc.Plug.AuthorizationCallback.init(opts))`:
    ```elixir
    [
      provider: provider.worker,
      client_id: provider.client_id,
      client_secret: Espalier.Identity.Oidc.client_secret(provider),
      client_context_opts: Espalier.Identity.Oidc.client_context_opts(provider),
      client_profile_opts: %{profiles: [], require_pkce: true, trusted_audiences: []},
      redirect_uri: provider.redirect_uri,
      preferred_auth_methods: Espalier.Identity.Oidc.auth_methods(provider),
      retrieve_userinfo: false,
      check_peer_ip: true,
      check_useragent: true,
      request_opts: Espalier.Identity.Oidc.request_opts()
    ]
    ```
    - `auth_methods/1` returns `[:private_key_jwt]` for certificate clients, `[:client_secret_basic]` for `google` and for `entra` with a development secret, and the configured method for `oidc`. The one-element list stops oidcc from moving on to another method without a report.
    - The plug deletes its session key and writes `{:ok, {token, userinfo}}` or `{:error, reason}` to `conn.private[Oidcc.Plug.AuthorizationCallback]`. With `retrieve_userinfo: false`, the result `{:error, {:none_alg_used, token}}` is never treated as success. Read the raw ID token and its claims from the `Oidcc.Token` struct; check the field names in `deps/oidcc/lib/oidcc/token.ex` and `deps/oidcc/lib/oidcc/token/id.ex`. The access and refresh tokens in the struct are dropped here and stored nowhere.
    - The action runs `Rules.check/4` and then, by purpose:
      - `sign_in`: `sign_in_external/2`. The ticket gets `auth_methods` `[:oidc, :idp_mfa]` when `Rules.idp_mfa?/2` holds and `[:oidc]` otherwise.
      - `link`: `check_external_link/3`. The callback writes no identity. The ticket gets `auth_methods` `[:oidc]` and `link_identity` with `issuer`, `tenant_id` and `subject` of the assertion, and `{:ok, :already_linked}` proceeds like `:ok`.
      - `step_up`: `check_external_step_up/3`, and `Rules.idp_mfa?/2` must hold, otherwise the reason is `:amr_single_factor`. The ticket gets `auth_methods` `[:oidc, :idp_mfa]`.
    - On success the action calls `create_login_ticket/1` with the user id (from `sign_in_external/2`, or from the transaction for `link` and `step_up`), the purpose, `idp_amr` from the assertion and `idp_sid_hash` set to `UserToken.hash_idp_sid(assertion.sid)`, which is `nil` when the ID token carries no `sid` (step 6). It clears the transaction session, stores `"ticket_binding"` in it with `put_session/3`, and redirects to `/auth/finish#ticket=<ticket>`. The fragment keeps the ticket out of server logs and the `Referer` header. The transaction cookie stays until the finish step, because it carries the binding.
    - On failure, the action drops the transaction session, logs `authn_login_fail` with the reason, and redirects to `/auth/finish?error=<code>`:

    | Code | Causes |
    |---|---|
    | `oidc_cancelled` | The provider returned `error=access_denied`. |
    | `oidc_unavailable` | The worker has no configuration, the provider is unreachable, an endpoint lies outside `AUTH_<KEY>_ALLOWED_HOSTS`, or no PKCE method is available. |
    | `oidc_no_account` | No identity matches, and provisioning is off or the verified e-mail address belongs to another account. |
    | `oidc_identity_in_use` | A link attempt names an identity of another account. |
    | `oidc_failed` | Every other failure: state, nonce, PKCE, signature, algorithm, audience, expiry, `iss`, a missing transaction, a provider mismatch, tenant, hosted domain, group overage, missing claims, stale `auth_time`, a single-factor `amr` at step-up, a disabled account, a second identity of the same provider, a step-up for another identity, an invalid intent, or an intent opened without the session that created it. |

11. **Intents for linking and step-up.** `EspalierWeb.OidcIntentController.create/2` handles `POST /api/auth/oidc/:provider/intents` with `{"purpose": "link" | "step_up"}`.
    - An unknown key answers 404 with `{"error": "unknown_provider"}`. A session whose strength is `demo` answers 403 with `{"error": "forbidden"}`, so only sessions of strength `mfa` create intents.
    - `link` requires a second factor within the last 10 minutes. The controller checks `Scope.recent_auth?/1` and otherwise answers 403 with `{"error": "reauth_required"}`, the code of `require_recent_auth/2` (README section 6.10). It answers 409 with `{"error": "provider_already_linked"}` when the user already holds an identity of this provider.
    - `step_up` requires an identity of this provider on the current user and `mfa: :idp_trusted`. Otherwise it answers 422 with `{"error": "step_up_not_available"}`. Users of `local` providers step up with `POST /api/me/reauth` from 0005.
    - The answer is 201 with `{"url": "/auth/oidc/<key>?intent=<token>"}`, which the SPA opens as a top-level navigation. The intent works only together with the browser session that created it (steps 7 and 9). The bucket `oidc_intent` allows 10 requests per minute per user: the controller calls `EspalierWeb.Plugs.RateLimit.check_account(conn, :oidc_intent, user.id)` of 0004, which answers 429 with `retry-after` and logs `excess_rate_limit_exceeded` on a denial, and continues only when `conn.halted` is false.

12. **Finish.** `EspalierWeb.Auth.FinishController.create/2` serves `POST /api/auth/finish` with the body `{"ticket": ...}` under the `:api` pipeline, so the request passes the CSRF token check and carries the `Strict` session cookie. The bucket `auth_ip` of 0004 applies.
    - The action reads `"ticket_binding"` from the transaction cookie with `TransactionCookie.get(conn, "ticket_binding")` (0004 step 32). Every response of this route deletes the transaction cookie with `TransactionCookie.clear(conn)`.
    - When `consume_login_ticket/2` fails, the answer is 401 with `{"error": "ticket_invalid"}`, and `authn_login_fail` is logged. A ticket injected into another browser fails here, because that browser holds no matching binding.
    - The answers follow README section 6.12: `{"next": "second_factor"}`, `{"next": "enroll_second_factor"}`, or the session payload of `GET /api/session` for a full session, with `"linked": true` after a link.
    - `sign_in` with a ticket without `:idp_mfa` (`mfa: :local`, or `idp_trusted` with a single-factor `amr`): when `Accounts.enrolled?/1` holds, `UserAuth.put_pending_second_factor(conn, user, %{auth_methods: [:oidc], provider_key: ticket.provider_key, idp_sid_hash: ticket.idp_sid_hash})` stores the pending state of 0004, and the answer is 200 with `{"next": "second_factor"}`. Otherwise `UserAuth.log_in_user(conn, user, auth_methods: [:oidc], strength: :enrollment, provider_key: ticket.provider_key, idp_sid_hash: ticket.idp_sid_hash)` creates the enrollment session of 0005, and the answer is 200 with `{"next": "enroll_second_factor"}`.
    - Sessions in `local` mode keep their provider link through the second factor and through the enrollment: 0005 step 14 passes `provider_key` and the bytes of `idp_sid_hash` that `fetch_pending_second_factor/1` of 0004 returns to `log_in_user/3`, and `Factors.complete_enrollment/3` (0005 step 12) passes those of the enrollment session row. Without these fields, front-channel logout finds no session of a `local` provider. Every later row of the session (step-up, re-authentication, password change) copies both fields through `reissue_session/2` or the copy of `PUT /api/me/password` (step 6). The flow tests of step 17 check each of these paths.
    - `sign_in` with a ticket that holds `:idp_mfa`: `UserAuth.log_in_user(conn, user, auth_methods: [:oidc, :idp_mfa], strength: :mfa, mfa_at: DateTime.utc_now(:second), provider_key: ticket.provider_key, idp_sid_hash: ticket.idp_sid_hash, idp_amr: ticket.idp_amr)` creates a full session. The answer is 200 with the session payload of 0004 step 35 (`EspalierWeb.SessionJSON`), which carries the new CSRF token, and without `next`.
    - `link`: the current session's user must equal the ticket's user. Otherwise the answer is 401 `ticket_invalid`, and nothing is linked. On a match the action calls `link_external_identity(user.id, provider, ticket.link_identity)`. `{:ok, :linked}` and `{:ok, :already_linked}` answer 200 with the session payload and `"linked": true`. `{:error, :identity_in_use}` answers 409 with `{"error": "identity_in_use"}`, and `{:error, :provider_already_linked}` answers 409 with `{"error": "provider_already_linked"}`.
    - `step_up`: the current session's user must equal the ticket's user, otherwise the answer is 401 `ticket_invalid`. Extend `UserAuth.step_up/2` of 0005 to `step_up(conn, method, changes \\ %{})`, which merges `changes` into the changes it passes to `reissue_session/2`; `method` joins `auth_methods` only when it is absent, as in 0005. The action calls `UserAuth.step_up(conn, :idp_mfa, %{idp_amr: ticket.idp_amr})`. The reissue keeps `expires_at`, copies `provider_key` and the bytes of `idp_sid_hash` unchanged, sets `mfa_at` to the current time and logs `session_renewed` (0004 step 18), and `step_up/3` puts the new token with `UserAuth.put_reissued_session/2` of 0004, which rotates the CSRF token. The action logs `authn_login_success` with `purpose: "step_up"`, and the answer is 200 with the session payload, which carries the new CSRF token.

13. **Logout.**
    - `front_channel_logout/2` serves `GET /auth/oidc/:provider/front-channel-logout`. An unknown key answers 404. When `iss` is present and differs from `provider.issuer`, the action ends nothing. When `sid` is present, `delete_sessions_by_idp_sid/2` ends the matching sessions, and `session_logout` is logged with `trigger: "front_channel"` and the count. The answer is always 200 with an empty body and `Cache-Control: no-store`. The bucket `oidc_front_channel` allows 60 requests per minute per IP.
    - Entra ID loads the front-channel URL in an iframe, so the allowlist of the `:oidc_transaction` pipeline (0004 step 32) admits this path with `Sec-Fetch-Site: cross-site` and `Sec-Fetch-Dest: iframe`. The request carries no platform cookie, the action reads and writes no session, and `sid` is its only link to a session. The default CSP with `frame-ancestors 'none'` stays, because the sessions end on the server before the browser applies the policy.
    - RP-initiated logout extends `DELETE /api/session` (0004). The action reads `provider_key` from `conn.assigns.current_scope.session` before `log_out_user/1` deletes the row. When the key names a configured OIDC provider whose loaded configuration passes `check_endpoints/2`, the action builds a client context with `Oidcc.ClientContext.from_configuration_worker(provider.worker, provider.client_id, :unauthenticated, %{})` and calls `:oidcc_logout.initiate_url(:undefined, Oidcc.ClientContext.struct_to_record(client_context), %{post_logout_redirect_uri: PUBLIC_URL <> "/signed-out"})`. `{:ok, url}` answers 200 with `{"logout_url": IO.chardata_to_string(url)}`. A configuration outside the allowlist, `{:error, :provider_not_ready}` from either call and `{:error, :end_session_endpoint_not_supported}` keep the 204 of 0004, so Google sessions, whose discovery document has no `end_session_endpoint`, end locally.
    - The URL carries `client_id` and `post_logout_redirect_uri` and no `id_token_hint`, because the platform keeps no ID token. The action calls the Erlang function, because `Oidcc.Logout.initiate_url/3` of oidcc 3.9.0 raises `CaseClauseError` for `:undefined` (Notes). `/signed-out` is the post-logout page of README section 6.12, which 0011 renders.

Fixtures live in `Espalier.DevOidc.Fixtures`.

    | Profile | Issuer | Discovery differences |
    |---|---|---|
    | `entra` | `http://localhost:P/entra/<T>/v2.0` | no `code_challenge_methods_supported`, no `token_endpoint_auth_signing_alg_values_supported`, `subject_types_supported` `["pairwise"]`, `token_endpoint_auth_methods_supported` `["client_secret_basic", "private_key_jwt"]`, `end_session_endpoint`, `frontchannel_logout_supported: true` |

    - Every discovery document has `issuer`, `authorization_endpoint` (`<issuer>/authorize`), `token_endpoint` (`<issuer>/token`), `jwks_uri` (`<issuer>/jwks`), `response_types_supported` `["code"]`, `response_modes_supported` `["query"]`, `subject_types_supported` (`["public"]` outside `entra`), `id_token_signing_alg_values_supported` `["RS256"]`, `grant_types_supported` `["authorization_code"]` and `scopes_supported` `["openid", "profile", "email"]`. oidcc 3.9.0 rejects a discovery document whose `scopes_supported` lacks `openid`. OpenID Connect Discovery marks the field as recommended.
    - For the keys, the Agent generates `JOSE.JWK.generate_key({:rsa, 2048})` at start, with `kid` from `JOSE.JWK.thumbprint/1`. `GET <issuer>/jwks` returns the map from `JOSE.JWK.to_public_map/1` (which returns `{meta, map}`) with `"kid"`, `"alg" => "RS256"` and `"use" => "sig"`. ID tokens are signed with `JOSE.JWT.sign(jwk, %{"alg" => "RS256", "kid" => kid}, claims)` and `JOSE.JWS.compact/1`. The `kid` must be in the JWS map, because a `kid` stored on the JWK does not reach the compact token.
    - `GET <issuer>/authorize` checks that `client_id` is known, that `redirect_uri` exactly equals a registered URI, that `response_type` is `code`, that `scope` contains `openid`, that `state` is present, and that `code_challenge` is present with `code_challenge_method=S256`. A failed check redirects with `error=invalid_request`, for the `entra` profile as well. The page is plain HTML: one button per fixture user of the profile and a "Deny" button, each a form that posts the request parameters and the fixture id to `<issuer>/authorize/decision`. Every value is escaped with `Plug.HTML.html_escape/1`.
    - `POST <issuer>/authorize/decision` redirects to `redirect_uri` with `error=access_denied` and `state` for "Deny". Otherwise it stores a code (32 random bytes, Base64url) with client id, redirect URI, challenge, nonce, fixture, `max_age` and `auth_time` for 60 seconds, and redirects with `code` and `state`. The `google` profile adds `iss=<issuer>`.

The `entra` profile also accepts `private_key_jwt`: it verifies `client_assertion` with `JOSE.JWT.verify_strict/3`, the algorithms `["RS256", "PS256"]` and the key registered with `put_client_key/2`, and checks `iss` and `sub` equal to the client id, `aud` equal to the issuer (or to the token endpoint under the switch `{:assertion_aud, :token_endpoint}`), `exp` in the future and an unused `jti`. Any other method answers 401 `invalid_client`, and the request log records every token request with the method, the assertion header and whether a `dpop` header was sent.
    - The token endpoint deletes the code on first use, so a second use answers 400 `invalid_grant`, as do an expired code, another client id, another `redirect_uri` and a PKCE mismatch.     - `GET <issuer>/logout` (profiles `entra` and `oidc`) checks `post_logout_redirect_uri` against the registered URIs, records the call and redirects there.
    - All fixture users are invented, with addresses under `example.org` and `example.net`. ## Notes
- oidcc 3.9.0 (2026-08-30) fixes CVE-2026-75759 (GHSA-533g-4vf3-xwrj): versions from 3.2.0-beta.1 through 3.8.x accepted an ID token or JARM response that was encrypted and unsigned. oidcc_plug 0.5.0 (2026-08-04) fixes CVE-2026-66884, a callback without an `Authorize` session that was processed with every check disabled, and CVE-2026-66883, a user-agent binding that never matched. Hex retired 0.5.0 for an invalid igniter version requirement, which makes 0.5.1 the minimum. oidcc 3.8.0 raised the minimum to OTP 27 and Elixir 1.17. Sources: hex.pm package pages and the GitHub advisories, retrieved 2026-10-07.
- Hex 2.5.1 makes `mix hex.audit` exit non-zero for retired packages and for packages with security advisories (README section 13). Hex has not retired oidcc 3.2.0-beta.1 through 3.8.x, and whether its advisory data lists GHSA-533g-4vf3-xwrj is unverified, which is why step 1 lists oidcc directly.
- oidcc talks HTTP through OTP `:httpc` by default, so `Req.Test` cannot intercept it, and the tests use the mock over loopback. oidcc 3.8.0 added a pluggable `http_adapter`. The worker's `provider_configuration_opts.request_opts` apply to discovery and JWKS only, and token, userinfo, introspection and pushed authorization requests need their own `request_opts` (oidcc 3.9.0, `src/oidcc_http_adapter.erl`).
- oidcc 3.9.0 builds every authorization request through `attempt_par/3` (`src/oidcc_authorization.erl`). When the discovery document names `pushed_authorization_request_endpoint`, it posts the request there with client authentication and the `request_opts` of the `Authorize` options, and it returns `par_required` when the document requires pushed authorization requests without naming the endpoint. Step 5 therefore checks that endpoint, and step 9 passes the adapter of step 5.
- oidcc 3.9.0 signs a request object (`attempt_request_object/3`, `src/oidcc_authorization.erl`) when the discovery document sets `request_parameter_supported` to `true`, with the client key or the client secret. It signs a DPoP proof (`dpop_proof/4`, `src/oidcc_auth_util.erl`) and adds `dpop_jkt` to the authorization request when the document names `dpop_signing_alg_values_supported` and the client has a key. The overrides of step 5 switch both off. A provider whose document sets `require_signed_request_object` to `true` then fails closed with `request_object_required`.
- `allow_unsafe_http` relaxes the `https` check only for `userinfo_endpoint`, `end_session_endpoint`, `pushed_authorization_request_endpoint` and `mtls_endpoint_aliases`. Issuer, authorization, token, JWKS and registration endpoints accept any scheme (oidcc 3.9.0, `src/oidcc_provider_configuration.erl`, `decode_configuration`).
- In oidcc 3.9.0, `Oidcc.Logout.initiate_url/3` matches its first argument against a binary or an `%Oidcc.Token{}` and raises `CaseClauseError` for `:undefined`. Its `@spec` lists `:undefined` as an accepted value. `:oidcc_logout.initiate_url/3` drops every query parameter whose value is `undefined`, always adds `client_id`, and returns `{error, end_session_endpoint_not_supported}` when the discovery document has no `end_session_endpoint`. Sources: `lib/oidcc/logout.ex` and `src/oidcc_logout.erl` of oidcc 3.9.0.
- `:oidcc_provider_configuration_worker.get_provider_configuration/1` returns the configuration record or `undefined`, and `oidcc_client_context:from_configuration_worker/4` returns `{error, provider_not_ready}` for an unloaded worker (oidcc 3.9.0).
- With `preferred_auth_methods: [:private_key_jwt]` and no `token_endpoint_auth_signing_alg_values_supported`, `oidcc_auth_util:add_client_authentication/6` of oidcc 3.9.0 gets `auth_method_not_possible` for `private_key_jwt`, retries with the remaining advertised methods, and `select_preferred_auth/2` returns `{error, no_supported_auth_method}` before any token request. The negative test of step 17 relies on this.
- On oidcc `main` after 3.9.0, and unreleased on 2026-10-07: #559 retries failed JWKS loads (in 3.9.0 a retry after a JWKS failure reloads the whole configuration), #558 switches the worker's ETS table to `set`, #557 returns an error for non-https URIs, and #556 fixes the start and the returned wait of the `random_exponential` backoff. oidcc_plug `main` has #96 for the JWKS refresh with client stores after 0.5.1. The `:discovery_down` test of step 17 covers the 3.9.0 behaviour.
- oidcc_plug stores the nonce, the PKCE verifier, the peer IP, the user agent and `:erlang.phash2/1` of `state` in the Plug session, and no provider. That hash has 27 bits and is no cryptographic hash, so PKCE and the nonce carry the binding of code and token to the transaction. Phoenix's cookie store signs without encrypting unless `encryption_salt` is set, which is why the transaction cookie of 0004 sets it.
- RFC 9700 section 4.4.2.2 requires a client that uses distinct redirect URIs as its mix-up defense to compare the redirect URI where the response arrived with the issuer of the request and to abort on a mismatch. Step 10 implements this with the provider key in the transaction session.
- An intent is a bearer value in the query string, and it can leak through proxy logs or browser history. It works once, for 5 minutes, and only with the session row that created it (steps 7 and 9), and `filter_parameters` keeps it out of the Phoenix request log. The session binding and the link at finish keep an intent from attaching the identity of whoever opens the URL to the account that created it (README section 6.2, rule 3; ASVS 10.1.2). The authorization response carries `code` and `state` in the query string as well; `code` is single-use and bound to the PKCE verifier. The row ASVS 14.2.1 of `docs/security/asvs-l2.md`, which 0011 owns, records the intent and the authorization response as a deviation with these measures.
- `check_peer_ip` compares `conn.remote_ip` at authorize and callback. It binds the flow to the client address only when 0004 derives `remote_ip` from the trusted proxy (README section 6.10).
- The discovery documents of Google and of Entra ID (the `common` and `organizations` documents and a tenant document), retrieved 2026-10-08, list `["RS256"]` as `id_token_signing_alg_values_supported`. Entra's documents carry neither `token_endpoint_auth_signing_alg_values_supported` nor `code_challenge_methods_supported`, which step 5 adds as overrides (README section 15, decision D13).
- Microsoft documents the certificate assertion with the header `x5t#S256` (`alg` "Should be PS256") and `aud` equal to the token endpoint. oidcc 3.9.0 sends `alg` and `kid` only, with `aud` equal to the issuer by default. draft-ietf-oauth-rfc7523bis-11 (26 March 2026, RFC Editor queue) requires the issuer as the sole `aud` value. oidcc issue #473 reports that Entra accepts the thumbprint in `kid`. These differences are the reason for the spike in step 18.
- Entra ID advertises `self_signed_tls_client_auth`. oidcc implements `tls_client_auth` only, and only with `request_opts.ssl`, so the platform does not use mutual TLS.
- `department` is absent from Entra's optional claims. Claims mapping needs `acceptMappedClaims` or a custom signing key, and with a custom key the discovery URL needs `?appid=`, which oidcc 3.9.0 cannot fetch, because it rejects issuers with a query.
- Microsoft does not document the query parameters of the front-channel logout request. Third-party reports name `sid` and sometimes `iss`; step 18 records what the tenant sends.
- Google treats the `hd` request parameter as a user interface hint and asks applications to check the `hd` claim and to key users by `sub`. Google's discovery document (retrieved 2026-10-07) advertises `authorization_response_iss_parameter_supported: true`, `client_secret_post` and `client_secret_basic`, and no `end_session_endpoint`.
- In `local` mode, the first federated sign-in of a user without a factor leads to enrollment, so whoever passes the provider's sign-in first binds the first local factor. The guide states this for operators who switch provisioning on.
- With `AUTH_<KEY>_PROVISION=false`, a person gets access through an invitation (0004), the enrollment of a passkey or of a password with TOTP (0005), and a link from the security settings. Invitations go only to users without an external identity (0004 step 19), so the invitation comes before the link. After the link, the account signs in through the provider, and its passkey, TOTP factor or recovery codes serve as second factor (step 20).
- `Oidcc.ClientContext.from_manual/5` builds a client context from a static configuration and JWKS, which allows token validation tests without HTTP when a case does not need the mock.
- The rate-limit numbers in steps 9 to 13 are initial values. README section 6.10 sets no numbers for these buckets.
