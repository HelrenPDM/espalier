## Goal
The self-assessment, interest votes and feedback are stored without a link to
the person, and each person counts once. Reports for analysts aggregate the
anonymous rows and count credentials per qualification and status, and every
report applies a minimum group size. The competence report groups the item
statistics by the competence area and depth of the learning objectives that the
items name, so that an analyst sees the share correct per CORE area and depth
of a program. A nightly job reorders the anonymous
tables and deletes old rows once an operator sets retention periods, and an
optional client-only log supports usability tests.

## Steps
1. Generate the schemas, each command through `nix-shell --run "..."`. The three anonymous tables have no user and use `--no-scope`. `participation_markers` belongs to a user and uses the default scope from 0004, which adds `user_id` itself; the command therefore names no `user_id`, and nobody adds one by hand.
   - `mix phx.gen.context Insights SelfAssessmentResponse self_assessment_responses program_id:references:programs segment_key:string org_unit:string recorded_on:date --no-scope --merge-with-existing-context`
   - `mix phx.gen.schema Insights.InterestVote interest_votes companion_format_id:references:companion_formats choice:string recorded_on:date --no-scope`
   - `mix phx.gen.schema Insights.FeedbackResponse feedback_responses program_id:references:programs answers:map recorded_on:date --no-scope`
   - `mix phx.gen.schema Insights.ParticipationMarker participation_markers subject_type:string subject_id:uuid`
   `--merge-with-existing-context` lets the generator append to `lib/espalier/insights.ex` without a prompt when 0009 has written that module (Phoenix 1.8.15, `lib/mix/tasks/phx.gen.context.ex`). `subject_id` uses the generator type `uuid`, which the list of valid types in `lib/mix/phoenix/schema.ex` contains. For the scoped schema, the template `priv/templates/phx.gen.schema/migration.exs.eex` writes `add :user_id, references(:users, type: :binary_id, on_delete: :delete_all)` and `create index(:participation_markers, [:user_id])`, and the schema gets `changeset/3` with the scope as third argument. In that migration, set `null: false` on `user_id`, `subject_type` and `subject_id`, keep `on_delete: :delete_all`, and add a unique index on `(user_id, subject_type, subject_id)`. The three anonymous tables and `participation_markers` have no `inserted_at` or `updated_at`: remove `timestamps()` from these four schemas and migrations.
2. Primary keys are random UUIDs from the project default of `--binary-id`. The generated schemas set `@primary_key {:id, :binary_id, autogenerate: true}`, and for a `:binary_id` key the adapter calls `Ecto.UUID.bingenerate/0` (ecto_sql 3.14.0, `lib/ecto/adapters/sql.ex`), which produces version 4 UUIDs by default (Ecto 3.14.2, `lib/ecto/uuid.ex`). Version 7 would need the type `Ecto.UUID` with `autogenerate: [version: 7]`. Keep the generated key definition in the four schemas; `Repo.insert_all/3` in step 3 fills the `:binary_id` key through the same adapter function. The nightly `CLUSTER` in step 10 orders the rows by this key, so a time-ordered key (UUID version 7) would keep the insertion order visible.
3. `Insights.record_once(scope, subject, fun)` in `lib/espalier/insights.ex` runs in one transaction. It inserts the marker with `Repo.insert_all(ParticipationMarker, [row], on_conflict: :nothing, conflict_target: [:user_id, :subject_type, :subject_id])`, where `row` holds `user_id` from `scope.user.id`, `subject_type` and `subject_id`. A returned count of 1 means the marker is new, and `fun` inserts the anonymous row. A count of 0 means the marker existed, and the function returns `{:ok, :already_recorded}`. `Repo.insert/2` with `on_conflict: :nothing` returns `{:ok, struct}` with a client-generated id in both cases, so it cannot tell the two cases apart (Ecto 3.14, documentation of `Repo.insert/2`, section on upserts). The subject types are `self_assessment` (subject: the program id), `format_vote` (subject: the companion format id) and `feedback` (subject: the program id). `org_unit` is copied from `scope.user.org_unit` only when `insights_org_unit` in `config :espalier, :learning` (0009 step 9, `INSIGHTS_ORG_UNIT`) is true, and `recorded_on` is the current UTC date.
4. Each endpoint has an OpenApiSpex operation and `CastAndValidate` in the `EspalierWeb.ApiSpec` of 0009, as 0009 does for its learner routes. The operations of the routes of this task belong to this task, as the Scope of 0009 states for the learner routes of 0013 and 0014; their request and response schemas live under `lib/espalier_web/schemas/` with the prefix `EspalierWeb.Schemas`, and every request schema sets `additionalProperties: false` (0009 step 3). All four routes sit in the `/api` scope under `pipe_through [:api, :authenticated]`, so the router-wide CSRF test of 0004 covers the three POST routes.
   - `POST /api/self-assessments {program_slug, segment_key}` records the answer through `record_once/3` and, for a new answer, calls `Learning.apply_default_path(scope, program, path)` with the segment's default path, both inside one transaction. This task adds `apply_default_path/3`: the function creates the enrollment with the segment's default path when none exists, and it changes the path of an existing enrollment only while `path_chosen_manually` is false. The response is `{"path": <path>, "already_recorded": <boolean>}`; for an answer that was already recorded, the enrollment stays unchanged.
   - `POST /api/formats/:id/votes {choice}` accepts the choice `would_use`.
   - `POST /api/feedback {program_slug, answers}` validates the answers against the questions in the `config` of the feedback station. Free-text answers are accepted only when `FEEDBACK_FREE_TEXT=true` (step 10) and are limited to 2,000 characters.
   - `GET /api/me/participation?program=slug` returns `{"self_assessment": <boolean>, "feedback": <boolean>, "format_votes": [<format id>]}` from the markers of the user and holds no answer.
   Run `make api-types`, so that `frontend/src/api/schema.d.ts` contains the new operations.
5. The stations of steps 5 to 7 live under `src/learner/stations/`, and each one is added to the station map `src/learner/stations/index.ts` of 0012 for its kind. The self-assessment station (`kind: self_assessment`) shows the question from the station `config`, one card per segment (label and description), an explanation that the answer is stored without the person's name and only preselects the path, and a skip link. Choosing a segment preselects its default path from the catalog view of 0009, posts the self-assessment, and shows the returned path with the path switch of 0012. A skip leaves the enrollment as 0012 creates it. A second visit reads `GET /api/me/participation`, shows the current path with the path switch, and states that the answer was already recorded.
6. The companion formats station (`kind: companion_formats`) shows one card per format with phases, description and a "Would use" toggle. The toggle posts once, and the station states that the choice is anonymous and cannot be changed afterwards.
7. The feedback station (`kind: feedback`) renders the questions from `config` (single choice, scale 1 to 5, free text) and accepts one submission per person. Free-text questions appear only when `flags.feedbackFreeText` from `toSession()` (step 11) is true.
8. Reports for the role `analyst` are the six routes of the row Reports in README section 8. All of them sit in the `/api` scope under `pipe_through [:api, :analyst]`, and each returns cells with `{count, value}` or `{suppressed: true}` when the count is below `INSIGHTS_MIN_GROUP_SIZE` (step 10). README section 10 limits the reports to the anonymous rows and to the count of credentials per qualification and status.
   - `GET /api/insights/self-assessment?program=slug` returns the distribution of segments by month, and by org unit when `INSIGHTS_ORG_UNIT` is true.
   - `GET /api/insights/items?program=slug` returns the attempts and the share correct per item and month from `item_stats`.
   - `GET /api/insights/competence?program=slug` returns the share correct of the items of the program grouped by the competence area and the depth of the learning objectives that the items name through `item_objectives`, by month, and by org unit when `INSIGHTS_ORG_UNIT` is true. The paragraph after this list describes the function behind it.
   - `GET /api/insights/formats?program=slug` returns the "would use" count per format of the program from `interest_votes`.
   - `GET /api/insights/feedback?program=slug` returns the choice and scale distributions. It returns free-text answers only when their total count reaches the threshold, and then in random order.
   - `GET /api/insights/credentials?program=slug` returns the count of credentials per qualification of the program and status (`active`, `refresh_due`, `expired`, `revoked`) from `credentials` (0013).
   No report returns a user id, a display name or a per-person row. Write the suppression in one function used by every report, and test it with counts below, at and above the threshold. Each route has an OpenApiSpex operation, as in step 4.
   The competence report is `Insights.competence_report(scope, program_slug)` in `lib/espalier/insights.ex`. An item has no area and no depth of its own (0008 step 2), so the function reads both only through `item_objectives` and the table `learning_objectives`:
   - Links. A subquery selects the distinct triples of item id, objective area and objective depth of the program: `from i in Item, join: o in assoc(i, :objectives), where: i.program_id == ^program.id and is_nil(i.archived_at) and is_nil(o.archived_at) and i.kind != ^:poll, distinct: true, select: %{item_id: i.id, area: o.area, depth: o.depth}`, with `Item` and `LearningObjective` from `Espalier.Catalog`. Ecto casts the interpolated `^:poll` through the `Ecto.Enum` type of `kind`. With `distinct: true`, an item that names two objectives of the same area and depth counts once in that group, and an item that names objectives of two areas or two depths counts in the group of each. A poll stays out of the report, because it has no correct answer and 0009 increments only its `attempts`. Archived items and objectives stay out as well, as in `Catalog.Alignment.matrix/1` for a `%Program{}` (0008 step 13), so the report follows the current alignment of the program.
   - Grouping. The query joins `item_stats` (0009) on the item id of the subquery and groups by area, depth and `period`, and also by `org_unit` when `insights_org_unit` in `config :espalier, :learning` is true. With the setting false, `org_unit` stays out of `group_by` and `select`, so that statistics written while the setting was true sum into one group per area, depth and month. Each group yields `sum(s.attempts)` and `sum(s.correct)`.
   - Cells. The count of a cell is the sum of `attempts`, and its value is the share correct, `correct / attempts`, as a number from 0 to 1. The suppression function replaces every cell whose count is below `INSIGHTS_MIN_GROUP_SIZE` with `{suppressed: true}`, so the share of a suppressed cell never leaves the server. A month in which a row has no statistics gives the count 0 and is suppressed as well.
   - Response. The body is `{"by_org_unit": <boolean>, "months": [<date>], "rows": [{"area", "depth", "org_unit", "cells": [...]}]}`. `months` lists every `period` of the result in ascending order as an ISO 8601 date on the first day of the month, and each row holds one cell per entry of `months` in the same order. `org_unit` is `null` when `by_org_unit` is false, and in the row that sums the answers of users without an org unit. The database stores the enums as strings, so the function orders the rows in Elixir: by area in the order of `Ecto.Enum.values(LearningObjective, :area)` (`subject`, `method`, `self`, `social`), then by depth in the order of `Ecto.Enum.values(LearningObjective, :depth)` (`know`, `apply`, `judge`), then by org unit. A combination of area and depth without statistics has no row. The response schema `EspalierWeb.Schemas.CompetenceReport` declares `area` and `depth` as string enums with these values.

The retention job `Espalier.Insights.RetentionWorker` in `lib/espalier/insights/retention_worker.ex` is registered as `{"30 3 * * *", Espalier.Insights.RetentionWorker}` in the `Oban.Plugins.Cron` crontab of `config :espalier, Oban` that 0004 step 8 sets up. The four retention variables are unset by default, and an unset variable leaves its tables untouched, so no record is deleted automatically until the GDPR workstream (README section 10) decides the retention periods and an operator sets them. For each variable that is set, the job deletes the rows older than the limit:
    - `item_responses` by `answered_on` for `RETENTION_ITEM_RESPONSES_DAYS`;
    - `self_assessment_responses`, `interest_votes` and `feedback_responses` by `recorded_on` for `RETENTION_ANONYMOUS_DAYS`;

    The job logs the deleted count per table and logs `unset` for each variable without a value. Afterwards, on every run and whatever the retention settings, it runs `CLUSTER self_assessment_responses USING self_assessment_responses_pkey` and the same statement for `interest_votes` and `feedback_responses`, so that the physical row order follows the random keys.

## Notes
- The participation marker answers "has this person answered" and nothing else. Never join it with the anonymous tables, and keep it out of every report.
- Anonymity holds against every role of the application. A database administrator can still correlate insertion order between two reorder runs, and so can the write-ahead log and backups. The GDPR workstream (README section 10) documents this limit for operators.
- The retention periods are part of the GDPR workstream (README section 10). This task builds the mechanism and ships it with every period unset.
- Free text can identify its author. The threshold rule for free text is the minimum; operators can switch free text off.
- This task depends on 0012 for the station navigation, the station map and the path switch, and on 0013 for the table `credentials`, which the credentials report and the retention rule for attempts read. Through 0012 and 0013 it builds on 0008, 0009 and 0010; the competence report reads `learning_objectives` and `item_objectives` of 0008 and `item_stats` of 0009.
- The competence report reads `item_stats`, which 0009 fills from practice answers only (0009 step 13, README section 10). Exam items therefore appear in no cell. An objective whose only evidence is a companion format, as the `self` and `social` objectives of the demo pack, appears in no row, because no report covers attendance certificates (README section 10).
- An item that names objectives of two areas or two depths counts in the row of each, so the cells of one month can sum to more than the attempts of the same items in `GET /api/insights/items`.
- `item_stats` holds no objective. The report assigns the statistics of an item to the objectives the item names when the report runs, so a pack version that changes the objectives of an item, or the area or depth of an objective, moves the earlier months of that item to the new rows. No table stores a status per objective and person (README section 7, rule 15), and this report adds none.
- The registrar list and the attendance routes of the facilitator are outside this task, because 0013 owns them. The reports of this task show analysts counts only. Following README section 10, no report covers enrollments, module completions, exam attempts, acknowledgements or attendance certificates.
- README section 7, rule 1: the SPA preselects the segment's default path, and the learner can switch it. The server stores that path through `apply_default_path/3`, so that a manual choice keeps priority over a later self-assessment. The enrollment stores the path. It never stores the segment.
