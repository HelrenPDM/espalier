## Goal
People sign in with the account of their organization's directory, either
Active Directory or a generic LDAP server. A read-only service account searches
the person, a bind on a second TLS connection verifies the password, mapped
directory groups become roles, and the person continues to the local second
factor, or enrolls one at the first sign-in. A durable counter, reserved before
each bind, keeps the platform below the directory's lockout threshold. The
adapter is a thin wrapper around `:eldap` behind a behaviour. Mox tests and an
in-process fake LDAP server cover it without a directory, and integration tests
run against lldap over LDAPS.

## Security requirements
The ownership table of 0004 step 42 names this task as owner of these rows of `docs/security/asvs-l2.md`:

- 12.3.4: The trust anchors of the directory connections come only from `AUTH_<KEY>_CA_CERT_FILE`; the operating system trust store is not used.
- 13.2.1: The service account authenticates with a password because `:eldap` offers only `simple_bind`; the matrix records this as a deviation with the mitigations from 13.2.2 and 13.3.1.
- 13.2.2: The guide requires a dedicated service account that can only read user objects below the base DN.

The table names this task as extending task of these rows, with the owning task in brackets:
- 6.1.1 (0004): The guide and `docs/security/authentication.md` document the throttling buckets, the directory failure limit and lock period, how they keep the platform below the directory's lockout threshold, and how malicious lockout is limited and undone (step 31).
- 6.1.3 (0004): `docs/security/authentication.md` documents the LDAP pathway with the directory bind as first factor, a local second factor, and the enrollment session after a first sign-in without a factor.
- 6.3.1 (0004): Hammer limits requests per IP (IPv6 reduced to the /64 prefix), per typed account name and per directory subject, and a durable counter, reserved before each bind, limits failed binds per directory account, also under concurrent requests.
- 6.3.3 (0005): A directory bind alone yields at most an enrollment session, which reaches only the enrollment routes of 0005 and ends after 30 minutes. A full session needs a local passkey or TOTP.
- 6.3.7 (0004, Level 3): Linking a directory identity sends the notification "a sign-in method was linked" and logs `user_updated`.
- 6.3.8 (0004, Level 3): Unknown user, wrong password, disabled account, lock, subject throttling and directory errors return the same status, body and minimum response time.
- 6.8.1 (0006): Directory identities are keyed by provider key and `objectGUID` (or `entryUUID`) and are never matched by e-mail or user name.
- 6.8.2 (0006): The row states that the requirement does not apply to the directory, because a directory bind returns no signed assertion.
- 6.8.4 (0006): The directory reports no authentication strength, and the documented fallback treats the bind as a single factor.
- 12.1.1 (0017): The TLS options of the directory connections allow only TLS 1.3 and TLS 1.2.
- 12.3.1 (0004): Plain LDAP is refused outside dev and test, and a StartTLS answer other than the bare `:ok` aborts the sign-in.
- 12.3.2 (0006): Every directory connection uses `verify: :verify_peer` with hostname verification through `server_name_indication`.
- 13.3.1 (0003): The bind password comes from the runtime environment and never from the repository.
- 16.2.5 (0003): No `{log, fun}` option is passed to `:eldap`, and no exception text from inside the LDAP task reaches the log.
- 16.3.1 (0004): Every LDAP sign-in attempt, success or failure, writes a security event with factor and provider.
- 16.3.4 (0004): A failed LDAPS connect starts at most one TLS probe per provider and minute, and the probe logs the TLS alert as the operational event `directory_tls_failed` without credentials.
- 16.5.1 (0004): Every failure returns one generic error code without internals.
- 16.5.2 (0006): The platform keeps operating when the directory fails: each sign-in runs in a supervised task with a hard timeout, the kill of that task ends its handles, and a handle is never reused after an error or timeout.
- 16.5.3 (0003): An unreachable directory, a failed group lookup, a referral or a timeout fails the sign-in.

6. TLS and connection options. Build the TLS options once per provider:
   ```elixir
   tls_opts =
     [verify: :verify_peer, cacerts: config.cacerts, server_name_indication: config.host,
      versions: [:"tlsv1.3", :"tlsv1.2"]] ++
       if config.tls_wildcard,
         do: [customize_hostname_check: [match_fun: :public_key.pkix_verify_hostname_match_fun(:https)]],
         else: []
   ```
   - `ldaps`: `client.open([config.host], port: config.port, ssl: true, sslopts: tls_opts, timeout: config.timeout_ms)`.
   - `starttls`: `client.open([config.host], port: config.port, timeout: config.timeout_ms)` without `sslopts`, because `sslopts` alone switches `:eldap` to LDAPS. Then `client.start_tls(handle, tls_opts, config.timeout_ms)`. Only the bare atom `:ok` continues. `{:ok, {:referral, _}}` leaves the connection in plain text, so it closes the handle like every error and returns `:tls_failed`.
   - `none` (dev and test only): `client.open([config.host], port: config.port, timeout: config.timeout_ms)`.

   The option list for `open/2` never contains `:log`, `:anon_auth` or `:tcpopts`. `server_name_indication` is always set, because StartTLS otherwise checks the certificate against the peer IP address. A failed `open/2` returns `:connect_failed`.
7. Directory profiles. `Espalier.Identity.Ldap` selects the following per profile. `user_filter` is `:eldap.or(for attr <- config.user_attrs, do: :eldap.equalityMatch(attr, username))`, where `username` is the trimmed input as a binary.

   | Item | `ad` | `generic` |
   |---|---|---|
   | Search filter | `:eldap.and([:eldap.equalityMatch(~c"objectCategory", ~c"person"), :eldap.equalityMatch(~c"objectClass", ~c"user"), user_filter])` | `:eldap.and([:eldap.equalityMatch(~c"objectClass", ~c"person"), user_filter])` |
   | Attributes (charlists) | `objectGUID`, `userPrincipalName`, `sAMAccountName`, `mail`, `displayName`, `userAccountControl`, plus the org unit attribute | `entryUUID`, `uid`, `mail`, `displayName`, `cn`, plus the org unit attribute |
   | Subject | `objectGUID` converted by `object_guid_to_uuid/1` (step 10) | `entryUUID` normalized with `Ecto.UUID.cast/1` |
   | Disabled check | `userAccountControl` parsed as an integer; bit `0x2` set, a missing value or a value that does not parse rejects the entry | none |
   | Group filter per mapped group | `:eldap.extensibleMatch(group_dn, type: ~c"memberOf", matchingRule: ~c"1.2.840.113556.1.4.1941")` | `:eldap.equalityMatch(~c"memberOf", group_dn)` |
   | Login and UPN | `sAMAccountName` and `userPrincipalName` | `uid` and no UPN |
   | Display name | `displayName` | `displayName`, otherwise `cn` |

   `type` and `matchingRule` must be charlists, because `extensibleMatch/2` throws on binaries. The group DN may be a binary.
8. Input guards. `Espalier.Identity.Ldap.authenticate/4` checks its input before it starts a task or opens a connection. The username and the password must be binaries, valid UTF-8 (`String.valid?/1`) and not blank after `String.trim/1`. The username may have at most 256 bytes and the password at most 1,024 bytes. The search uses `String.trim(username)`, and the user bind sends the password unchanged. The password receives no Unicode normalization: it never passes through `PasswordPolicy.prepare/1` of 0004 step 14, whose NFC rule covers only local passwords (README section 6.4, the password row of the table, and section 15, decision D12). The directory server holds the stored password and compares the bind value by its own rules, so the bind carries the bytes that the user sent. Before the user bind, the DN from the search must pass the same blank check. Every guard failure returns `:invalid_input`. These guards exist because `:eldap` blocks only the empty charlist: an empty Elixir binary as password goes out as an unauthenticated bind, and an empty binary DN with an empty password goes out as an anonymous bind, and both return `:ok` from a server that accepts them.
9. Connection 1 in `lookup(config, username)`:
   1. Open the connection (step 6) and bind with `config.bind_dn` and `config.bind_password`. Anything other than `:ok` returns `:service_bind_failed`.
   2. Search with `base: config.base_dn, scope: :eldap.wholeSubtree(), filter: ..., attributes: [...], size_limit: 2, timeout: max(div(config.timeout_ms, 1000), 1)`. The search `timeout` is the server-side time limit in seconds. The `open/2` timeout is in milliseconds.
   3. Map the result. `{:ok, eldap_search_result(entries: entries)}` continues, and the `referrals` field is ignored, because the wrapper chases no referrals. `{:ok, {:referral, _}}` returns `:referral`, and `{:error, _}` returns `:unavailable`.
   4. Require exactly one entry. No entry returns `:not_found`, and two or more return `:ambiguous`. The count is the control, because `size_limit` is only a request to the server (lldap 0.6.3 ignores it).
   5. Convert the entry. The DN is `:erlang.list_to_binary(object_name)`. Attribute names are converted the same way and compared after `String.downcase/1`, and every value is converted with `:erlang.list_to_binary/1`. `List.to_string/1` is never used, because it double-encodes UTF-8 bytes. The display name is trimmed and cut to 200 code points, as 0006 step 8 does for the `name` claim.
   6. Apply the disabled check of the profile (`:disabled`) and compute the subject (`:no_identity_attribute` when it is missing or malformed).
   7. For every `{role, group_dn}` in the role map, search with `base: dn, scope: :eldap.baseObject(), filter: group_filter, attributes: [~c"1.1"], size_limit: 1` and the same timeout. One entry adds `group_dn` to the matched groups. Zero entries and `{:error, :noSuchObject}` (lldap's answer for a non-member) add nothing. Any other result returns `:group_lookup_failed`. Step 17 maps the matched groups to roles.
   8. Close the handle with `client.close/1` in an `after` block. After any error or timeout on a handle, no further request goes to that handle, because `:eldap` does not match search responses by message id and a late reply would answer the next request.
   9. Return `{:ok, %Espalier.Identity.Ldap.Entry{dn, subject, login, upn, email, display_name, org_unit, groups}}`, where `groups` lists the matched group DNs without duplicates.
10. GUID conversion. Write:
    ```elixir
    def object_guid_to_uuid(<<a::little-32, b::little-16, c::little-16, rest::binary-size(8)>>),
      do: Ecto.UUID.load(<<a::32, b::16, c::16, rest::binary>>)

    def object_guid_to_uuid(_), do: :error
    ```
    The first three fields of an `objectGUID` are little-endian, and the last eight bytes keep their order. The unit test uses the MS-ADTS example: the bytes `[63, 105, 46, 202, 128, 98, 137, 69, 147, 118, 179, 112, 115, 69, 211, 173]` give `{:ok, "ca2e693f-6280-4589-9376-b3707345d3ad"}`, and a 15-byte value gives `:error`.
11. Connection 2 in `verify_password(config, entry, password)`. Apply the DN and password guards, open a new connection with the same transport (step 6), and bind with `entry.dn` and the password. Map the result: `:ok` returns `:ok`; `{:error, :invalidCredentials}` returns `:bind_failed`; `{:ok, {:referral, _}}` returns `:referral`; any other `{:error, atom}` result code returns `:bind_rejected`; every other error returns `:unavailable`. Close the handle in an `after` block. The user bind never runs on the service connection, because a failed bind leaves that connection anonymous.
12. Orchestration in `authenticate(config, username, password, opts)`:
    1. Run the guards of step 8.
    2. Start `Task.Supervisor.async_nolink(Espalier.Identity.LdapTaskSupervisor, fn -> ... end)` and wait with `Task.yield(task, 3 * config.timeout_ms) || Task.shutdown(task, :brutal_kill)`. A `nil` result returns `:unavailable`, and an exit returns `:internal`. Add `{Task.Supervisor, name: Espalier.Identity.LdapTaskSupervisor}` to the children in `Espalier.Application`. `:eldap` links each handle process to its caller, so the kill also ends the open handles.
    3. Inside the task, call `lookup/2`, then `opts[:before_bind].(entry)`, then `verify_password/3`. `before_bind` returns `{:ok, ticket}` or `{:error, reason}`, and an error skips the user bind. The default `before_bind` returns `{:ok, nil}`.
    4. Wrap the task body in `try` with `rescue` and `catch`, and return `:internal` on any exception. Log only the exception module, because a `FunctionClauseError` carries the call arguments, which can include the password.
    5. Return `{:ok, entry, ticket}` or `{:error, reason, entry_or_nil, ticket_or_nil}`. A killed or crashed task returns `{:error, reason, nil, nil}`.

15. Directory failure counter. Extend `Espalier.Accounts.FailureCounters` (0004 step 17) with the following functions for the authenticator `:ldap`. They count an attempt before its bind, so concurrent requests cannot pass the check together. In this step, `n` is the count after the reservation, `limit` is `failure_limit` and `period` is `lock_minutes`.
    1. `reserve_directory(provider_key, subject, limit, period, now)` runs in `Repo.transact/1`. It inserts `%FailureCounter{authenticator: :ldap, provider_key: provider_key, subject_hash: ExternalIdentity.hash_input("ldap:" <> provider_key, nil, subject), consecutive_failures: 0}` with `on_conflict: :nothing` and `conflict_target: {:unsafe_fragment, "(authenticator, provider_key, subject_hash) WHERE subject_hash IS NOT NULL"}`, and then loads the row with `lock: "FOR UPDATE"`. A row with `disabled_at` set returns `{:error, :counter_disabled}`, and a row whose `locked_until` lies after `now` returns `{:error, :locked}`. Otherwise the function sets `consecutive_failures` to `n`, sets `locked_until` to `now` plus `period` when `n >= limit`, and returns `{:ok, %{id: id, count: n, previous_locked_until: old, locked_until: new}}`. The row lock lasts only for this transaction and never spans a directory call.
    2. `directory_succeeded(reservation)` deletes the row by id.
    3. `directory_failed(reservation, now)` keeps the count. It sets `disabled_at` to `now` and returns `:disabled` when `reservation.count >= 50`, returns `:limit_reached` when `reservation.count == limit`, and returns `:counted` otherwise.
    4. `release_directory(reservation)` runs in `Repo.transact/1`. It loads the row with `lock: "FOR UPDATE"`, lowers `consecutive_failures` by one without going below 0, and restores `previous_locked_until` when `locked_until` still holds the value this reservation set. A missing row means that a concurrent success deleted it, and the function then does nothing.
    5. `reset_directory(scope, provider_key, subject)` requires the role `admin` in the scope, which `Scope.system/0` holds, and returns `{:error, :forbidden}` otherwise. It finds the row through the hash input of step 14 with the issuer `"ldap:" <> provider_key`, deletes it, writes the audit event `failure_counter.reset` with the provider key in `details`, and logs `user_updated` with `provider` and `reason: "directory_counter_reset"`. `reset_directory_for_user(scope, user)` does the same for every identity of the user whose provider key names an LDAP provider; it computes the hash input from the identity's issuer, tenant and decrypted subject.
    6. README section 6.10 keeps a disabled authenticator disabled until recovery. The recovery pathway of 0005 step 16 serves local accounts without an external identity, so it never reaches a directory account, and `FailureCounters.clear_all/1` of 0005 never sees directory rows, because they carry no `user_id`. A locked or disabled directory counter is therefore cleared by `reset_directory_for_user/2`, which the admin action "reset failure counters" of 0015 calls (README section 8, decision D11), or by the release function of item 7.
    7. Add `Espalier.Release.reset_directory_lock(provider_key, username)`. It loads the application as the release functions of 0004 step 24 do, looks up the entry with `Ldap.lookup/2` through the service account, calls `reset_directory(Scope.system(), provider_key, entry.subject)`, and prints `:ok`, `{:error, :not_found}` or `{:error, :unavailable}`. The function also covers directory accounts that have no platform account yet.

    The lock policy differs from README 6.10, which delays from the fifth failure with 30 seconds doubling up to one hour. A directory account needs a limit below the directory's lockout threshold and a lock period that covers the directory's lockout counter reset time, so that the directory's own counter has reset when the next bind arrives. Step 32 records this difference and the admin reset of item 6 as deviations in `docs/security/authentication.md`.

31. Guide. Add a section "Active Directory" to `docs/guides/identity-providers.md`, which 0006 step 20 creates as a draft, and a short section "Generic LDAP and the development lldap" with the values of step 28 and every variable of step 4, including `AUTH_LDAP_TLS_WILDCARD`. The Active Directory section covers these points:
    - The service account is a dedicated account that can only read user objects below the base DN and has no write rights. Its password is the only stored directory credential. The section explains the ASVS 13.2.1 deviation and the rotation of that password.
    - Active Directory serves LDAPS on TCP 636. The domain controller's certificate needs the Server Authentication EKU `1.3.6.1.5.5.7.3.1` and the controller's FQDN in a SAN DNS entry, or in the subject CN when the certificate has no SAN. `AUTH_LDAP_HOST` must be that name, and the issuing CA chain goes as PEM into `AUTH_LDAP_CA_CERT_FILE`. The operating system trust store does not contain an internal CA and is not used. Wildcard certificates need `AUTH_LDAP_TLS_WILDCARD=true`.
    - New Windows Server 2025 deployments enforce LDAP signing by default, and the domain controller then rejects password binds over unencrypted connections (Microsoft Learn, "LDAP signing"). Channel binding applies only to SASL over TLS, so binds over LDAPS or StartTLS are unaffected.
    - The default filter accepts both `sAMAccountName` and `userPrincipalName`. `sAMAccountName` has at most 20 characters. Neither attribute is a stable key, and Active Directory accepts many name forms in a bind, including `displayName`, which is why the platform searches first and binds with the returned DN.
    - The platform keys the account on `objectGUID`, converted to a UUID, so renames of DN, UPN or `sAMAccountName` keep the account.
    - A set `userAccountControl` bit `0x2` rejects the sign-in before the bind. The platform does not read the lockout state from `userAccountControl`, because Active Directory keeps it in `msDS-User-Account-Control-Computed`.
    - The operator reads the account lockout threshold and the lockout counter reset time of the domain, and of any fine-grained password policy for platform users. `AUTH_LDAP_FAILURE_LIMIT` goes below the threshold, and `AUTH_LDAP_LOCK_MINUTES` goes to at least the reset time. The platform cannot see the reason codes in Active Directory's bind errors.
    - A person who knows a user name can start the platform lock without the password. The lock blocks only the directory pathway of that account on the platform, and the directory's own lockout stays out of reach while the two settings above hold. After the first lock, one attempt per lock period reaches the directory, so the counter reaches 50 and disables the pathway after 50 minus `AUTH_LDAP_FAILURE_LIMIT` further lock periods; with a limit of 4 and 30 minutes, that takes 23 hours. An account with an external identity signs in only through its directory or a linked provider, and its passkey serves as second factor (0005 step 8), so the lock keeps a directory-only account out of the platform until the lock period ends. The recovery pathway serves local accounts only (0005 step 16). An admin clears the counters of an account in the admin area (0015), and the operator clears any directory counter, also of a person without a platform account, with `bin/espalier eval 'Espalier.Release.reset_directory_lock("<key>", "<user name>")'`.
    - Role map entries are group DNs. The platform checks membership transitively with the matching rule `1.2.840.113556.1.4.1941`, with one search per mapped group and sign-in, so the operator keeps the map short.
    - The platform rejects empty passwords itself. The operator may additionally enable `DenyUnauthenticatedBind` (MS-ADTS), which defaults to 0.
    - Each provider key covers one domain. The platform follows no referrals and uses no Global Catalog. Every directory user has a local second factor (`AUTH_LDAP_MFA=local`), and the first sign-in enrolls a passkey or TOTP.
    - A person with a local account links the directory account in the security settings, which requires a second factor from the last 10 minutes (step 20). After the link, the account signs in only through the directory, followed by its passkey, its TOTP factor or a recovery code as second factor. Password sign-in, passkey sign-in without a prior first factor and the recovery pathway serve only accounts without an external identity (0004 step 16, 0005 steps 8 and 16), so the stored password serves no sign-in after the link.
    - The plan defines no route that removes an external identity. An account that holds an identity of an LDAP provider therefore has no sign-in pathway once that provider key leaves `AUTH_PROVIDERS`, unless the account holds an identity of another configured provider. The admin reset of decision D11 (0015) sends an invitation only to accounts without an external identity, so it does not restore access either. The operator keeps a provider key configured as long as accounts depend on it.

- The `:eldap` behaviours of this task come from `lib/eldap/src/eldap.erl` at tag `OTP-28.5.0.7` (eldap 1.2.16.1). OTP 28.5 ships eldap 1.2.16, and eldap 1.2.16.1 of OTP 28.5.0.6 and 28.5.0.7 adds a fix for the port parsing of referral URLs (OTP-20345). `eldap.erl` at `OTP-29.1.1` is byte-identical to `OTP-28.5.0.7`. With Elixir 1.20.4 on OTP 28.5.0.7, `:eldap` and `:ssl` behave as follows: an empty binary password and an empty binary DN both reach the server as `{:simple, []}` and return `:ok` from a server that accepts unauthenticated binds, such as the fake of step 22; the empty charlist returns `{:error, :anonymous_auth}`; a referral on the bind returns `{:ok, {:referral, [...]}}`; `timeout: :infinity` returns `{:error, {:wrong_option, {:timeout, :infinity}}}`; a binary host returns `{:error, ~c"connect failed"}`; `extensibleMatch/2` with a binary `type` throws `{:error, {:extensibleMatch_arg, ...}}`; LDAPS to an IP address without SNI, with a wrong SNI or with the OS trust store fails, and succeeds with the configured CA and SNI; StartTLS without SNI fails the hostname check against the peer IP address, and succeeds with SNI; `List.to_string/1` turns `Jürgen` into `JÃ¼rgen`, and `:erlang.list_to_binary/1` keeps it.
- The same source file shows these further behaviours. Search responses are not matched by message id, so a late reply after a timeout can answer the next search on the same handle. A handle whose owner exits normally stays open until `close/1`. `{log, fun}` receives the bind request with the cleartext password at the same level as connect errors. `start_tls/3` can return `{:ok, {:referral, _}}` without encrypting. `:eldap.info/1` reports `socket_type` `tcp` after a successful StartTLS and cannot prove encryption.
- `eldap.erl` at `OTP-28.5.0.7` sends StartTLS with message id 0 when it is the first operation on a handle, because `exec_start_tls` takes the current id without `bump_id`. RFC 4511 section 4.1.1.1 forbids message id 0 in a request. Whether Active Directory rejects such a request is open, and the Samba AD job below checks it. The fake of step 22 answers with the id of the request, so it accepts the id 0.
- lldap `v0.6.3` (image `lldap/lldap:v0.6.3`) behaves as follows towards `:eldap`: LDAPS on 6360 works with `verify_peer` and the test CA of step 28; users have the DN `uid=<id>,ou=people,<base>` and the object class `person`; `entryUUID` is returned as a UUID string; a member of the group `lldap_strict_readonly` can search; a base-scope search on a user DN with a `memberOf` equality filter returns the entry for a member and `{:error, :noSuchObject}` for a non-member; the IN_CHAIN rule returns `{:error, :unwillingToPerform}`; StartTLS returns `{:error, {:response, :unwillingToPerform}}`; an empty password returns `{:error, :invalidCredentials}`; the server ignores `size_limit`; the search result carries a paged-results control in `controls`; `/app/bootstrap.sh` creates users, groups and passwords from the JSON files. The v0.6.3 source has no disabled-user state, so the `userAccountControl` check is tested with Mox and the fake only.
- Filter escaping is not applied. The `:eldap` constructors build ASN.1 structures, and an assertion value goes out verbatim, so RFC 4515 escaping would change the value that the server compares.
- On OTP 28.5.0.7, the certificates that `:public_key.pkix_test_data/1` builds with its default key parameters fail the TLS 1.3 handshake with `unable_to_supply_acceptable_cert`. With `key: {:namedCurve, :secp256r1}, digest: :sha256` for root and peer, the handshake completes, which is why step 22 sets both.
- `:ELDAPv3` is an undocumented module of the `eldap` application, and the fake depends on it only in test code. In the nixpkgs build of OTP 28.5.0.7, the generated `ELDAPv3.hrl` lies in `eldap-1.2.16.1/ebin` and is missing from `eldap/include`, which is why the fake writes the tuples by hand.
- The Active Directory statements of this task cite these sources: MS-ADTS "Simple Authentication" for the name forms in a bind, MS-DTYP 2.3.4.2 for the GUID layout, MS-ADTS "LDAP Configurable Settings" for `DenyUnauthenticatedBind` with default 0, Microsoft Learn KB 305144 for the `userAccountControl` flags (ms.date 2026-02-12), KB 321051 for the LDAPS certificate requirements (ms.date 2026-02-12), the pages "LDAP signing" and "LDAP channel binding" (ms.date 2026-10-02), and "Search Filter Syntax" for `1.2.840.113556.1.4.1941`. `:eldap` discards the bind response's diagnostic message, so sub-codes such as `data 775` (locked) cannot be read.
- Directory counter rows carry no `user_id`, also after the identity exists. 0004 keeps a unique index on `(user_id, authenticator)`, and a user with identities at two LDAP providers would hold two `ldap` rows under it. Step 15 therefore reaches these rows through the user's identities for the admin reset of 0015.
- The reservation of step 15 holds a row lock only inside a short transaction. A lock across the bind would keep one database connection per sign-in busy for up to three times `AUTH_LDAP_TIMEOUT_MS`.
- The OpenAPI operations for `POST /api/auth/ldap/:provider` and `POST /api/me/identities/ldap/:provider` belong to 0011 (README section 6.12), which describes the routes of 0005, 0006 and 0007 with `open_api_spex` and `EspalierWeb.ApiSpec` of 0009. This task therefore adds no OpenAPI code and has no dependency on 0009.
- Some Debian packagings of Erlang ship `eldap` as a separate package (`erlang-eldap`). Whether the `hexpm/elixir` builder image of step 1.5 contains it is open, so step 1.5 and the release and container checks of the acceptance list establish it for the image that runs in production.

- A disabled or removed directory account takes effect at the next sign-in. Open sessions end at their inactivity or absolute timeout (60 minutes, 24 hours), and a directory synchronization job is out of scope.
- The first sign-in of a directory user enrolls a second factor on the strength of the directory password, in an enrollment session of 30 minutes. The factor notification from 0005 tells the user about the enrollment.
