## Goal
A learner walks through a program station by station: path choice, lessons
with collapsible explanations, every item kind with feedback, reveal on wrong
answers on the short path, the exam with the pass rule, module completion, the
rules recap, the glossary and the printable handbook. Each module station opens
with the learning objectives of its topic, grouped by the four competence
areas (subject, method, self and social competence). Every item shows the
objectives it serves, and the completion of a module shows which objectives
have evidence, which the learner has practised and which are open. The player
depends only on the `Runtime` interface, so that the admin preview of 0015 and
the SCORM build of 0016 reuse it, the objectives and their status included.

## Steps

### Runtime
1. Write `src/player/runtime.ts` with the `Runtime` interface of README section 9, unchanged, and the view types `ProgramView`, `ModuleView`, `ObjectiveView`, `ItemView`, `Answer`, `ItemFeedback`, `AttemptResult`, `ResumeState` and `ObjectiveStatus`. Derive the types from `src/api/schema.d.ts` with `import type` where the API defines them.
   - `ProgramView` holds the program of `GET /api/programs/:slug` with its stations, segments and companion formats, one `ModuleView` per module from `GET /api/modules/:id`, and the glossary of `GET /api/programs/:slug/glossary`.
   - `ModuleView` carries `objectives`, a list of `ObjectiveView` (schema `ObjectiveView` of 0009 step 12) with `key`, `statement`, `area` (`subject`, `method`, `self` or `social`), `depth` (`know`, `apply` or `judge`), `phase`, `domain` (a string or `null`), `lesson_ids` and `evidence` (entries `{kind, id}` with `kind` `item` or `format`), in the order of the module view. `ItemView` carries `objective_keys`, the keys of the objectives that the item serves.
   - `ResumeState` holds `path` (`short` or `full`), `openedExplanations` (block ids), `visitedStations` (station positions), `answeredItems` (item ids), `completedModules` (module ids), `examOutcomes` (assessment id to `passed`, `failed_core` or `failed_errors`) and `evidencedObjectives` (the objective keys whose evidence the runtime reports).
   - `ObjectiveStatus` is the union `"evidenced" | "practised" | "open"`. No runtime stores it; `objectiveStatus` of step 11 derives it.
   - `AssessmentsOpenError` extends `Error` and carries `assessments`, a list of `id`, `key` and `title` in the shape of the 409 `assessments_open` answer of 0009 step 13. `completeModule` of every runtime rejects with it while an exam of the module with `counts_for_credential: true` has no passed attempt.
2. Write `src/runtimes/platform.ts` with `PlatformRuntime`, which implements `Runtime` for one program with the API client `api` of 0010. The constructor takes the program slug and optional `client` and `storage` objects (`storage` with `getItem` and `setItem`), which the tests pass.
   - `loadProgram` calls `GET /api/programs/:slug`, then `GET /api/modules/:id` for every module and `GET /api/programs/:slug/glossary`.
   - `loadState` calls `GET /api/me/progress?program=<slug>`. When the answer holds no enrollment, it creates one with `POST /api/enrollments {program_slug, path: "full"}`, so every enrollment starts on the full path until 0014 adds the self-assessment. It takes `path`, `completedModules` and `examOutcomes` from the server, and `openedExplanations` and `visitedStations` from the `localStorage` entry. It takes `evidencedObjectives` from the `objectives` of the progress answer: the keys whose `status` is `evidenced`, under both settings of `TRACKING_DETAIL`.
   - With `TRACKING_DETAIL=standard`, the progress answer holds the ids of the answered items (0009 step 13), and `loadState` takes `answeredItems` from the server. With `TRACKING_DETAIL=minimal`, the answer holds no such ids, and `loadState` takes `answeredItems` from the `localStorage` entry, so that the resume state stays in the browser (README section 10). The runtime keeps the setting that the last progress answer showed.
   - `saveState` writes the `localStorage` entry. It writes `answeredItems` into the entry only when the last progress answer held no ids of answered items. It writes nothing of `completedModules`, `examOutcomes` and `evidencedObjectives`. When `path` differs from the path of the enrollment, it also sends `PATCH /api/enrollments/:id {path}`, which marks the choice as manual (0009 step 13).
   - `submitItem` posts `POST /api/items/:id/responses {answer}`, and `submitAssessment` posts `POST /api/assessments/:id/attempts {answers}`. `completeModule` posts `POST /api/modules/:id/completion` and rejects a 409 `assessments_open` with `AssessmentsOpenError`. Every other error answer rejects with an `Error` that carries the status and the error code; the middleware of 0010 handles 401 and `csrf` before that.
   - The `localStorage` key is `espalier.player.<program slug>`. With `TRACKING_DETAIL=standard`, its value is the JSON `{"v":1,"openedExplanations":[...],"visitedStations":[...]}`. With `TRACKING_DETAIL=minimal`, the value adds `"answeredItems":[...]`. The entry holds block ids and item ids of the catalog and station positions. It holds no user id, name, e-mail address, answer, correctness, exam result, objective key, objective status or timestamp, and an entry in `answeredItems` records only that an item was answered. Without an injected `storage`, `src/runtimes/platform.ts` reaches `localStorage` inside a `try/catch` around every access, and a missing, unreadable or malformed entry yields empty lists. Only `saveState` writes the entry, so it appears once a program page or a station page has been opened. No other module of the SPA reads or writes the key.
3. Write `src/player/RuntimeContext.tsx` with `RuntimeContext` and `useRuntime()`, and `src/player/usePlayer.ts`, which loads the program and the resume state once per runtime, keeps the state in React state, and passes every change through `saveState`. When `loadState` resolves `null`, the player starts on the `full` path with empty lists.
   - `usePlayer` also returns `refreshEvidence()`, which calls `loadState()` and replaces only `evidencedObjectives` in the React state. This change goes through no `saveState` call, because the list comes from the runtime. When `loadState` rejects or resolves `null`, the list stays unchanged.
   - Replace the placeholder routes `/`, `/programs/:slug` and `/programs/:slug/stations/:position` of 0010 step 8 in `src/app/router.tsx`, and add `/programs/:slug/glossary` and `/programs/:slug/handbook`, all under `RequireAuth`.
   - `src/learner/ProgramRoute.tsx` is the parent route of the four program routes. It creates one `PlatformRuntime` per slug and provides it through `RuntimeContext`.
   - Every UI string of this task goes through `t()`, with keys in `en.json` and `de.json`.

    - Objectives panel. `src/player/objectives/ObjectivesPanel.tsx` renders the `objectives` of the `ModuleView` at the top of the station, below the station heading and the path switch, in a `section` labelled by its `h2` heading "Objectives of this topic". It groups the objectives by area in the order of `AREAS` and renders one group per area that holds at least one objective of the module, with the area label as `h3` and the objectives as a list in the order of the module view. Each entry carries the id `objective-<key>` and `tabIndex={-1}`, and shows the statement, the depth label, the domain when the objective names one, and the lessons of `lesson_ids` as links with their titles. A lesson link has `href="#lesson-<lesson id>"`. Its click handler prevents the default, scrolls the lesson heading into view and moves focus to it, so that the link works under the browser router and under the memory router of 0016. A module view without objectives renders no panel. The panel shows no status.
    - Objective chips. `src/player/objectives/ObjectiveChips.tsx` takes the `objective_keys` of an item and renders a list labelled "Objectives of this item" with one chip per key that names an objective of a `ModuleView` of the `ProgramView`. A key without such an objective renders nothing. The visible text of a chip is the area label and the depth label, for example "Subject competence, Know". The statement is the accessible description of the chip (`aria-describedby`) and appears in a tooltip on hover and focus, which stays open while the pointer rests on it and closes with Escape (WCAG 2.2, 1.4.13). A chip of an objective of the current module links to `#objective-<key>` and moves focus to the panel entry in the way of the lesson links. A chip of an objective of another module links to the station of that module through React Router. Chips wrap on narrow screens, and each chip has a target size of at least 24 by 24 CSS pixels (WCAG 2.2, 2.5.8).
    - Objective status. `src/player/objectives/status.ts` exports the pure function `objectiveStatus(objective, program, state)`, which reads only its arguments. It returns `evidenced` when `state.evidencedObjectives` holds the key, or when `state.examOutcomes` maps an exam of `program` to `passed` and that exam holds an item whose id appears with kind `item` in the `evidence` of the objective. The second condition shows a pass of the current visit before the runtime reports it, and it follows the rule of 0009 step 13 for passed attempts. Otherwise the function returns `practised` when `state.answeredItems` holds the id of a practice item of `program` (an item of a lesson in any `ModuleView`) whose `objective_keys` hold the key, and `open` in every other case. `practised` records only that the learner answered a practice item for the objective, because `answeredItems` holds no correctness. `PlatformRuntime` fills `answeredItems`, `examOutcomes` and `evidencedObjectives` as step 2 describes, and `StandaloneRuntime` (0015) and the SCORM runtimes (0016) fill the same members of `ResumeState`, so that the panel, the chips and the status work through the `Runtime` interface under every runtime.
    - Completion. The "Complete module" button calls `completeModule`. On success the station adds the module to `completedModules`, calls `refreshEvidence()` of step 3, and shows the completion with the summary. The status region announces the completion and the number of objectives per status, and focus moves to the heading of the summary (`tabIndex={-1}`). On `AssessmentsOpenError` the station lists the open exams by title and shows no summary. A station whose module is in `completedModules` when it opens shows the completion and the summary.
    - Completion summary. `src/learner/CompletionSummary.tsx` lists the objectives of the module grouped by area in the order of `AREAS`, with the area labels as headings. Each entry shows the statement, the depth label and the status label of `objectiveStatus`. The status appears as text next to a Heroicon marked `aria-hidden`, so that no status depends on color alone (WCAG 2.2, 1.4.1). A sentence above the list gives the number of objectives per status through the plural forms of i18next. A legend explains the three statuses: `evidenced` means that an exam, an attendance certificate or a recorded practice answer shows the objective; `practised` means that the learner answered a practice item for it; `open` means that neither applies so far. An entry with the status `practised` or `open` whose `evidence` holds a format names that format by its title from the companion formats of the `ProgramView` and states that attendance there provides the evidence. When the `ProgramView` has a station of kind `companion_formats`, the note links to it. The summary shows no percentage, no progress bar and no comparison with other people.
12. Exam (`src/learner/ExamSection.tsx`): all items in one form; submit is enabled when every item has an answer. The result shows the outcome with its reason: `failed_core` (a core item is wrong), `failed_errors` (more wrong answers than the exam allows) or `passed` with the number of correct answers. It shows feedback per item and a "New attempt" button that clears the answers. The result shows no score percentage. The section records the outcome in `examOutcomes` of the player state and keeps `passed` for an exam once an attempt has passed, as the progress answer of 0009 step 13 does.
13. Glossary page (`src/learner/GlossaryPage.tsx`): an alphabetical list of the glossary of `ProgramView` with an anchor per slug.
