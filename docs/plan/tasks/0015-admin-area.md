## Goal
Authors upload, preview and publish content packs. Before a publish, the pack
page shows the alignment matrix of the pack and the findings of
`Espalier.Catalog.Alignment` with file and line. A publish is refused while the
strict alignment checks report an error, and the pack diff lists the added,
changed and archived learning objectives. Admins invite, disable and
reset users, end the sessions of one user or of all users, maintain policies,
the approved tool list, role grants, API clients and webhooks, revoke
credentials, and read the audit log. Facilitators issue attendance
certificates, analysts reach the reports of 0014, and registrars read the
credential list of 0013 while `REGISTRAR_ENABLED=true`. Every POST, PUT, PATCH
and DELETE route that this task adds under `/api/admin` requires a second factor
from the last 10 minutes (README sections 6.4 and 8), and with
`ADMIN_REQUIRE_PASSKEY=true` only admins who hold a passkey reach the admin
routes. All of it happens in the React admin area against JSON controllers with
OpenAPI operations.

4. **User administration.** `UserAdminController` serves `/api/admin/users` (README section 8). Every action passes the admin scope to `Espalier.Accounts`, and every function it calls writes an audit event and a security event (README section 6.10):

The link `/invite#token=` leads to an `enrollment` session, which enrolls a passkey or a password with TOTP (0005) before any other page. An address that has an account answers 409 `user_exists`.    - `POST /api/admin/users/:id/invitation` calls `Accounts.resend_invitation/2` of 0004 and answers 202, or 409 `not_invitable` for an enrolled user, a disabled user and a user with an external identity. Extend `resend_invitation/2` so that it writes the audit event `user.invitation_resent`.

7. **Pack upload, preview data and publication** (`PackController`, role `author`):
   - Upload parsing. Remove `:multipart` from the `Plug.Parsers` list in `lib/espalier_web/endpoint.ex`. With `pass: ["*/*"]`, the endpoint parser then leaves a multipart body unread and `body_params` unfetched (Plug 1.20.3, `lib/plug/parsers.ex`). Write `EspalierWeb.PackMultipart`, which wraps `Plug.Parsers.MULTIPART` with `length` taken from `PACK_UPLOAD_MAX_MB` (default 20, parsed in `config/runtime.exs`, added to `.env.example`), as the section "Dynamic configuration" of `lib/plug/parsers/multipart.ex` in Plug 1.20.3 shows. The pipeline `:pack_upload` runs `plug Plug.Parsers, parsers: [EspalierWeb.PackMultipart], pass: []` and serves only `POST /api/admin/packs`, behind `:author_write`, so that the server reads an upload only for an author with a recent second factor. A larger body answers 413 (`Plug.Parsers.RequestTooLargeError`), and another content type answers 415.
   - Archive checks in `Espalier.Catalog.Pack.Archive.extract(upload_path, max_bytes)`. `:zip` in OTP 28.5.0.7 (stdlib 7.3.0.3, `src/zip.erl`) rewrites an absolute entry name to a relative one, extracts an entry that climbs above the target directory under its last name component with the log line "Illegal path", and types every entry as a regular file or a directory with the permission bits only (`external_attr bsr 16 band 8#777` in `cd_file_header_to_file_info/3`). A symlink entry therefore arrives as a regular file that holds the link target, and neither `:zip.list_dir/2` nor `:zip.extract/2` reports it. The function therefore reads the central directory of the upload itself before any extraction: it locates the end-of-central-directory record, rejects ZIP64 and multi-disk archives, and reads name, uncompressed size, "version made by" and external attributes of every header. It rejects the archive, with one report entry per finding, when a name is absolute (leading `/` or `\`, or a drive letter), contains a backslash or a `..` component, when an entry made on Unix (upper byte of "version made by" equal to 3) carries the file type `0o120000` (symbolic link) in the upper 16 bits of its external attributes, when the archive holds more than 2,000 entries, or when the declared uncompressed sizes add up to more than five times the upload limit. After these checks, `:zip.extract/2` writes into a new directory below `System.tmp_dir!/0` (option `cwd:`), the function compares the size of every extracted file with its declared size and rejects the archive on a difference, and an `after` block removes the directory.
   - `POST /api/admin/packs` then runs `Espalier.Catalog.Pack.Importer.import/2` of 0008 on the directory with the author as actor and answers 201 with id, status and report. A rejected archive answers 422 with the report.
   - `GET /api/admin/packs/:id` returns status, report and, for a `validated` import, the payload including answer keys (authors only).
   - Alignment in the pack view. The answer of `GET /api/admin/packs/:id` also carries `alignment`, an object with `mode`, `matrix`, `errors` and `warnings`:
     - `mode` is the `alignment` value of the stored payload (`strict` or `warn`, 0008 step 9).
     - `matrix` holds the rows of `Espalier.Catalog.Alignment.matrix/1` on the stored payload, one per module, area and depth, each with `module`, `area`, `depth`, `objectives`, `lessons`, `evidence` and `elsewhere` (0008 step 13). Every module therefore has twelve rows.
     - An import without a stored payload answers `mode` and `matrix` as `null`. The importer stores no payload for a `failed` import (0008 step 9).
     - `errors` and `warnings` are the entries of the import report that come from `Alignment.check/1`, each with `file` (the path in the pack, for example `modules/01-basics/items.yaml`), `line`, `check` (1 to 4), `module`, `key` and `message`. The validator of 0008 writes each of these entries at the line of the objective, the item or the module area that it names, and it keeps `check`, `module` and `key` of the finding next to `file`, `line` and `message` (0008 steps 8 and 9), so every finding carries its file and line. `report` keeps every entry, and the page lists the entries with `check` in its alignment section and the others in the validation report.
   - `GET /api/admin/packs/:id/diff` compares the payload with the live tables of the program whose `slug` equals the pack key and lists the added, changed and archived keys per keyed kind of 0008 (modules, lessons, learning objectives, items, rules, assessments, qualifications, formats, sources, segments, glossary terms). Without such a program, every key of the payload appears under `added`. Live rows with `archived_at` set count as absent, so a key that a payload holds again appears under `added`, and a key whose row is already archived does not appear under `archived`. A key counts as changed when a value of the payload differs from its live row. An item and a format also count as changed when their list of objective keys differs from their `item_objectives` or `format_objectives` rows, and a module counts as changed when its `areas_elsewhere` differs.
   - Learning objectives in the diff. For a learning objective, the route compares `statement`, `area`, `depth`, `phase`, `domain`, `position` and the number of its module (`module`), the lesson keys of `taught_in` with the lessons of its `objective_lessons` rows (`taught_in`), and the keys of the items and formats that name it in the payload with its `item_objectives` and `format_objectives` rows (`items` and `formats`). Each list is compared as a sorted set, and a join row that points to an archived row counts as absent. The entry of the kind `learning_objectives` also carries `changed_fields`, a map from every changed key to the names of the fields that differ, for example `{"m1-method-check-claims": ["depth"]}`. A changed area or depth moves the objective to another row of the matrix and its items to another group of the competence report of 0014, and the author sees that change before the publish.
   - `POST /api/admin/packs/:id/publish` runs `Espalier.Catalog.Pack.Publisher.publish/1` of 0008 for a `validated` import and answers 409 `not_publishable` for any other status. A pack with an error from the strict alignment checks is stored as `failed` (0008 step 9) and therefore receives this answer.
   - Before the publisher runs, the controller calls `Espalier.Catalog.Alignment.check/1` on the stored payload. When the call returns at least one error, the route answers 409 `{"error": "alignment_errors", "findings": [...]}` with these errors, each with `check`, `module`, `file`, `key` and `message` as `check/1` returns them, and it does not call the publisher. With `alignment: strict` in the payload, every finding of checks 1 to 3 is an error. With `alignment: warn`, `check/1` returns warnings only, and the publish proceeds. The second check at publish time keeps a stored draft out of the live tables when the checks of the running release reject its payload, for example a draft that was stored before an update of `Espalier.Catalog.Alignment`.

9. **Standalone runtime.** `frontend/src/runtimes/standalone.ts` implements `Runtime` (README section 9) on a pack payload in memory and keeps state in memory. Write the shared fixture set `test/fixtures/evaluator_cases.json` (JSON cases of item, answer and expected result), which an ExUnit test and a Vitest test both read, so that both implementations return the same results.
   - `loadState` returns the state that the last `saveState` call stored, or `null` before the first call, and it returns `evidencedObjectives` as an empty list.
