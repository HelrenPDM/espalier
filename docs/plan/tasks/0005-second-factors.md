## Goal
Local accounts hold the second factors of README section 6.6. Passkeys are
discoverable credentials, verified by `wax_` 0.7.0 and by the checks the
application adds. TOTP accepts the current and the previous step, and each code
works once. Recovery codes are single-use secrets of 128 bits stored as HMACs.
A pending first factor from 0004 becomes a full session through
`POST /api/auth/second-factor`, a passkey alone signs in a local account, an invited
person enrolls a factor before any other page, a person who lost their factors
recovers with a saved recovery code and a link sent by e-mail, and every factor
change needs a second factor from the last 10 minutes.

## Security requirements
This list holds exactly the rows whose `Task` column names this task, as the ownership table of 0004 step 42 assigns them (README section 15, decision D16). A row marked "extends the row of" belongs to the task named there, and this task adds its code and test to that row.
- 2.3.1 (L1, extends the row of 0004): A pending first factor becomes a session only through a second factor (step 14), and an enrollment or recovery session becomes an `mfa` session only through a new factor (step 12).
- 6.1.1 (L1, extends the row of 0004): `docs/security/authentication.md` lists the buckets of step 18 and the counter kinds `:totp`, `:passkey` and `:recovery_code`, and states that a failed discoverable passkey sign-in counts only per IP, so that passkey sign-in stays available while the password counter of the account is locked.
- 6.1.3 (L2, extends the row of 0004): The same document lists the passkey, second-factor, enrollment and recovery pathways of this task with the session strength that each one reaches.
- 6.3.1 (L1, extends the row of 0004): The buckets of step 18 and the durable `:totp`, `:passkey` and `:recovery_code` counters limit guessing for every factor of this task.
- 6.3.3 (L2): A local account reaches a full session only with a passkey, or with a first factor and a second factor.
- 6.3.4 (L2, extends the row of 0004): Every pathway of this task ends in `log_in_user/3`, and the strength check of `create_session/2` raises for every method list that matches no clause of 0004 step 18 or of step 12.
- 6.3.5 (L3, extends the row of 0004): The account owner gets an e-mail after a sign-in that follows five or more failures of a second factor and when an authenticator is disabled.
- 6.3.7 (L3, extends the row of 0004): The account owner gets an e-mail after every added or removed factor, every regeneration of recovery codes and every recovery.
- 6.3.8 (L3, extends the row of 0004): `POST /api/auth/recovery/start` answers with the same status and body for known and unknown addresses, and every request causes one lookup and one job insert.
- 6.4.3 (L2): A password is set without the current one only in an `enrollment` session, which exists only for a user without a second factor, or in a `recovery` session, which needs a saved recovery code and a link sent by e-mail. A forgotten-password reset therefore never bypasses an enabled second factor.
- 6.4.4 (L2): A lost factor is replaced only after a saved recovery code and a link sent by e-mail, the two methods of README section 6.2.
- 6.5.1 (L2): Each TOTP code and each recovery code works once.
- 6.5.2 (L2): Recovery codes carry 128 bits and are stored as HMAC-SHA256 with a server key. ASVS allows a standard hash for look-up secrets of 112 bits or more.
- 6.5.3 (L2): TOTP secrets, recovery codes, challenges and user handles come from `:crypto.strong_rand_bytes/1`.
- 6.5.4 (L2): Recovery codes carry 128 bits, above the minimum of 20 bits.
- 6.5.5 (L2, extends the row of 0004; deviation, README section 15, decision D15): Recovery e-mail tokens expire after 10 minutes. TOTP accepts the previous 30-second step, as RFC 6238 section 5.2 recommends, and the section "Deviations" of the matrix records the departure from the 30-second limit.
- 6.5.6 (L3): Users remove passkeys and TOTP and regenerate recovery codes.
- 6.6.2 (L2): A recovery e-mail token works only for the latest recovery request of its user. A new request deletes the earlier tokens, and a successful verification deletes all of them.
- 6.6.3 (L2): `POST /api/auth/recovery/verify` is rate limited per IP and per user, the durable `:recovery_code` counter limits consecutive failures, and the e-mail token carries 256 bits.
- 7.2.4 (L1, extends the row of 0004): The second factor, the passkey sign-in, the recovery verification, the step-up and the completion of an enrollment or a recovery each issue a new session token and delete the previous session row.
- 7.4.3 (L2, extends the row of 0004): After a factor change or a recovery, the response offers to end the other sessions.
- 7.5.1 (L2, extends the row of 0004): Changes to factors and recovery codes need a second factor from the last 10 minutes.
- 11.4.1 (L1, extends the row of 0003; deviation, README section 15, decision D14): TOTP codes are HMAC-SHA-1 values, as RFC 6238 defines them by default and as `nimble_totp` 1.0.0 offers it, and the section "Deviations" of the matrix gives the reason.
- 11.5.1 (L2, extends the row of 0003): Recovery codes carry 128 bits, TOTP secrets 160 bits, WebAuthn challenges 256 bits and user handles 512 bits, each from `:crypto.strong_rand_bytes/1`.
- 11.6.1 (L2, extends the row of 0003; deviation, README section 15, decision D13): Passkey registration accepts only the COSE algorithms -7, -8 and -257 (step 9). -257 (RS256) serves Windows Hello authenticators, and the section "Deviations" of the matrix gives the reason.
- 16.2.5 (L2, extends the row of 0003): The `:filter_parameters` entries of step 2 keep TOTP codes and WebAuthn payloads out of the request log. No log line and no mail carries a code, a secret or a challenge, and security events name a credential only by the first 8 hex characters of the SHA-256 hash of its id.
- 16.3.1 (L2, extends the row of 0004): Every success and every failure of a passkey, TOTP or recovery-code verification is logged with the factor and the reason (step 20).
- 16.3.3 (L2, extends the row of 0004): Rescued `wax_` exceptions and rejected `clientDataJSON` are logged as `input_validation_fail`, and a sign count that does not increase is logged with `risk_signal`.
- 16.5.1 (L2, extends the row of 0004): Every check failure maps to the generic codes `authentication_failed` or `registration_failed` (step 9), and no response carries an exception message.

5. **Challenges and the ceremony id.** `Espalier.Accounts.Challenges`:

6. **Options JSON.** `Espalier.Accounts.Passkeys.Options` builds the JSON that `@simplewebauthn/browser` passes to the browser in 0011. Every binary is encoded with `Base.url_encode64(binary, padding: false)`.
   - `creation(user, challenge, credentials, config)` returns:
     ```json
     {
       "rp": {"id": "<config.rp_id>", "name": "<config.rp_name>"},
       "user": {"id": "<user.webauthn_user_handle>", "name": "<e-mail, else display name>", "displayName": "<display name, else e-mail>"},
       "challenge": "<challenge.bytes>",
       "pubKeyCredParams": [{"type": "public-key", "alg": -8}, {"type": "public-key", "alg": -7}, {"type": "public-key", "alg": -257}],
       "timeout": 300000,
       "excludeCredentials": [{"type": "public-key", "id": "<credential_id>", "transports": ["<stored transports>"]}],
       "authenticatorSelection": {"residentKey": "required", "userVerification": "required"},
       "attestation": "none"
     }
     ```
     `excludeCredentials` lists every credential of the user. The algorithm list holds only algorithms that `wax_` verifies: -8 (EdDSA), -7 (ES256) and -257 (RS256). WebAuthn Level 3 asks relying parties that support a wide range of authenticators to offer these three, and the FIDO metadata lists the Windows Hello authenticators with RS256 only. README section 15, decision D13, keeps -257, and the matrix records it as a deviation from ASVS 11.6.1.
   - `request(challenge, allow, config)` returns `{"challenge": ..., "timeout": 300000, "rpId": config.rp_id, "userVerification": "required"}`. It adds `allowCredentials` (type, id, transports) only when `allow` is a non-empty list, which happens for the purposes `second_factor` and `reauth`. The sign-in request carries no `allowCredentials`, which conditional UI needs.
   - `Espalier.Accounts.ensure_webauthn_user_handle(user)` runs `from(u in User, where: u.id == ^user.id and is_nil(u.webauthn_user_handle)) |> Repo.update_all(set: [webauthn_user_handle: :crypto.strong_rand_bytes(64)])` and reloads the user, so that concurrent requests keep one handle. The handle holds no personal data.

7. **Passkey registration.** `Espalier.Accounts.Passkeys.register(scope, challenge_row, params, config)`:
   1. Decode `rawId`, `response.clientDataJSON` and `response.attestationObject` with `Base.url_decode64(value, padding: false)`. A decoding error fails the registration.
   2. Run `ClientData.check(client_data_json, :create, config.origins)` (step 9).
   3. Rebuild the challenge with `Wax.new_registration_challenge(origin: config.origins, rp_id: config.rp_id, attestation: "none", user_verification: "required", timeout: 300, bytes: challenge_row.challenge)` and set `issued_at: DateTime.to_unix(challenge_row.expires_at) - 300` on the struct. `Wax.Challenge.new/1` keeps a given `bytes` option and always sets `issued_at` to the current time, so the override aligns the expiry check of `wax_` with the stored row. The struct never carries `allow_credentials`.
   4. Call `WaxCall.run(fn -> Wax.register(attestation_object, client_data_json, challenge) end)` (step 9).
   5. Apply the checks of step 9 for the COSE algorithm and for the backup flags, and require `raw_id == auth_data.attested_credential_data.credential_id`.
   6. Insert the credential with `credential_id`, `cose_key: auth_data.attested_credential_data.credential_public_key`, `sign_count: auth_data.sign_count`, `aaguid: Wax.AuthenticatorData.get_aaguid(auth_data)`, `backup_eligible: auth_data.flag_backup_eligible`, `backed_up: auth_data.flag_credential_backed_up`, `transports` (the values of `response.transports` that are one of `usb`, `nfc`, `ble`, `smart-card`, `hybrid`, `internal`) and an optional `nickname` of at most 60 characters. A credential id that any account already holds fails at the unique index.

8. **Passkey authentication.** `Espalier.Accounts.Passkeys.authenticate(challenge_row, params, expected_user_or_nil, config)`:
   1. Decode `rawId`, `response.clientDataJSON`, `response.authenticatorData`, `response.signature` and `response.userHandle`.
   2. Run `ClientData.check(client_data_json, :get, config.origins)`.
   3. Load the credential by `credential_id` with its user. An unknown credential fails.
   4. Apply the user handle rule of step 9. The owner of the credential is the user this assertion signs in; with `expected_user` set (second factor and re-authentication), the owner must be that user. Without `expected_user` (discoverable sign-in), fail with the reason `external_identity` when the owner holds an `external_identities` row. README section 6.2 lists passkey sign-in as a pathway of local accounts, and the OIDC and LDAP rows of that table start with the provider or the directory. A user with an external identity therefore signs in through the provider or the directory and uses a local passkey only as second factor, so the provider or the directory can still block the account, `idp_claim` grants are replaced at each sign-in, and the session row carries the `provider_key`.
   5. Fail when the user is disabled, or when the `FailureCounter` of kind `:passkey` of that user is locked or disabled (step 18).
   6. Rebuild the challenge with `Wax.new_authentication_challenge(origin: config.origins, rp_id: config.rp_id, user_verification: "required", timeout: 300, bytes: challenge_row.challenge)` and the `issued_at` override of step 7.
   7. Call `WaxCall.run(fn -> Wax.authenticate(credential.credential_id, authenticator_data, signature, client_data_json, challenge, [{credential.credential_id, credential.cose_key}]) end)`. The sixth argument is always the one resolved credential, because the challenge struct carries no `allow_credentials`.
   8. Apply the backup flag check and the sign count rule of step 9 to the returned `auth_data`.
   9. Update the row with one query: `sign_count` to `GREATEST(sign_count, new)` through `fragment/1`, `backed_up` to `auth_data.flag_credential_backed_up`, and `last_used_at` to now.

10. **TOTP.** `Espalier.Accounts.Totp`:
    - `start_enrollment(scope)` checks the existing row. An enabled factor in an `mfa` session returns `{:error, :totp_already_enabled}`. An enabled factor in a `recovery` session is deleted in the same transaction (notification "factor removed", step 19). A row without `enabled_at` is replaced. The function creates `secret = NimbleTOTP.secret()` (20 bytes) in a row with `enabled_at: nil`, builds `uri = NimbleTOTP.otpauth_uri("#{issuer}:#{label}", secret, issuer: issuer)` with the configured issuer and the e-mail address (else the display name) as label, renders `svg = uri |> EQRCode.encode() |> EQRCode.svg()`, and returns `%{qr_svg_data_url: "data:image/svg+xml;base64," <> Base.encode64(svg), secret_base32: Base.encode32(secret, padding: false), otpauth_uri: uri}`. The CSP of 0004 allows `img-src 'self' data:`, and the response carries `Cache-Control: no-store` from the header plug of 0004.
    - `verify(factor, code, now \\ System.os_time(:second))` requires `code =~ ~r/\A\d{6}\z/`. With `step = div(now, 30)`, the candidates are `step` and `step - 1`, each only when it is greater than `last_used_step` (or when `last_used_step` is nil). For each candidate `s`, it compares `NimbleTOTP.verification_code(secret, time: s * 30)` with the code through `Plug.Crypto.secure_compare/2`. On a match it runs `from(f in TotpFactor, where: f.id == ^factor.id and (is_nil(f.last_used_step) or f.last_used_step < ^s)) |> Repo.update_all(set: [last_used_step: s])`, and only `{1, _}` counts as success. This conditional update makes each code work once, also under concurrent requests. The module stores the matched step. `NimbleTOTP.valid?/3` takes a timestamp for its `:since` option, so the module calls `verification_code/2` per candidate step and skips `valid?/3`. Use only the options of NimbleTOTP 1.0.0 (`:time`, `:period`, `:since`); `:digits` and `:algorithm` exist only on unreleased master. The unit test pins that `verification_code/2` accepts `time:` as Unix seconds.
    - `confirm(scope, code)` verifies against the row without `enabled_at` and sets `enabled_at`. The confirmation code is then used, so it cannot sign in afterwards.
    - Sign-in, second factor and re-authentication accept only a factor with `enabled_at` set and a `FailureCounter` of kind `:totp` that is neither locked nor disabled.
    - `disable(scope)` deletes the row after the factor rules of step 12.

11. **Recovery codes.** `Espalier.Accounts.RecoveryCodes`:
    - `generate(scope)` deletes the user's rows and inserts ten new ones in one `Repo.transaction/1`. Each code is `Base.encode32(:crypto.strong_rand_bytes(16), padding: false)`: 26 characters from the base32 alphabet, 128 bits (README section 6.6). The function stores `code_hmac = :crypto.mac(:hmac, :sha256, key(), code)` and returns the display form: six groups of four characters and one group of two, joined by `-` (for example `ABCD-EFGH-IJKL-MNOP-QRST-UVWX-YZ`). Plain codes are never stored, logged or mailed.
    - `key/0` returns `:crypto.mac(:hmac, :sha256, hmac_secret, "espalier/recovery-codes/v1")`, where `hmac_secret` is `Base.decode64!(Application.fetch_env!(:espalier, Espalier.Hashed.HMAC)[:secret])`, the decoded `CLOAK_HMAC_SECRET` under the configuration key of 0003. The label separates this key from the lookup hashes of 0003.
    - `normalize(input)` upcases, removes whitespace and `-`, and requires `~r/\A[A-Z2-7]{26}\z/`.
    - `use(scope_or_user, input)` loads the user's rows without `used_at`, compares each `code_hmac` with the HMAC of the normalized input through `Plug.Crypto.secure_compare/2`, then runs `from(r in RecoveryCode, where: r.id == ^id and is_nil(r.used_at)) |> Repo.update_all(set: [used_at: now])`. Only `{1, _}` counts as success. It returns `{:ok, remaining}`.
    - `remaining(user)` counts rows without `used_at`. `generated_at/1` returns the `inserted_at` of the current set.

12. **Factor rules.** `Espalier.Accounts.Factors`:

14. **Second factor after a first factor, and passkey sign-in.**
    - `POST /api/auth/second-factor` takes exactly one of `{"totp": "123456"}`, `{"passkey": <AuthenticationResponseJSON>}` and `{"recovery_code": "ABCD-EFGH-..."}`. It requires the pending state that `fetch_pending_second_factor(conn)` of 0004 returns as `{:ok, %{user: user, auth_methods: methods, provider_key: key, idp_sid_hash: hash, expires_at: at}}`, with the methods as atoms, `idp_sid_hash` as bytes and `expires_at` as a `DateTime` five minutes after the first factor. For a missing or expired state and for a user who is not active, the function returns `:error`. It returns no conn and deletes nothing; `fetch_current_scope_for_user/2` of 0004 deletes an expired or malformed state on the next request of the `:api` pipeline. It verifies with `Totp.verify/3`, with `Passkeys.authenticate/4` (purpose `second_factor`, `expected_user` set to the pending user) or with `RecoveryCodes.use/2`. On success it clears the pending state and calls `UserAuth.log_in_user(conn, user, auth_methods: pending.auth_methods ++ [factor], strength: :mfa, mfa_at: now, provider_key: pending.provider_key, idp_sid_hash: pending.idp_sid_hash)`, where `factor` is `:totp`, `:passkey` or `:recovery_code`. `pending.idp_sid_hash` holds the bytes that `fetch_pending_second_factor/1` decodes from the Base64 value in the cookie (0004 step 33), or `nil`, so this step decodes nothing. The call issues a new session token and a new CSRF token, and the session row keeps the provider that README section 6.5 requires and the `sid` hash that the front-channel logout of README section 6.7 matches. It answers 200 with the body of `GET /api/session`; after a recovery code it adds `recovery_codes_remaining`. A missing or expired pending state, a wrong code, an unknown credential and a locked counter all answer 401 with the error code `authentication_failed`. The pending state counts failed attempts, and the fifth failure clears it, so the person starts again with the first factor. `fetch_pending_second_factor/1` returns no counter, so the count lives under the session key `pending_second_factor_failures`; the fifth failure deletes this key and `pending_second_factor` with `delete_session/2`, and `put_pending_second_factor/3` and `log_in_user/3` renew the session, which drops the count. This rule is a usability measure. The pending state lives in the client-side cookie store of 0004, and a client can resubmit an earlier cookie with a lower count; the limits that hold are the bucket `second_factor_user` of the pending user id (step 18) and the durable `:totp`, `:passkey` and `:recovery_code` counters.
    - Rule for `idp_sid_hash`: the value is the keyed hash of the provider's `sid` that 0006 computes once from the raw `sid` in its callback. The login ticket, the pending state and every later session row carry these bytes unchanged, and `create_session/2` and `reissue_session/2` of 0004 store them as given. This task never computes a hash of the value, never passes a raw `sid`, and never hashes a value that it read from a session row. It hands on the bytes of the pending state (this step) or of the current session row (steps 12 and 13). `delete_sessions_by_idp_sid/2` of 0006 compares the column with one keyed hash of the `sid` parameter, so a second hash at any of these steps would leave the session alive after the provider ends it. Before implementing steps 12 to 14, check in `lib/espalier/accounts/user_token.ex` that `idp_sid_hash` is a plain `:binary` field (0004 step 12); the acceptance test on the raw column bytes covers the pending state, the second factor, the step-up, the password change and the completion of an enrollment.
    - `POST /api/auth/passkey/options` takes `{"purpose": "sign_in" | "second_factor" | "reauth"}` with `sign_in` as default. `sign_in` issues a challenge without user and options without `allowCredentials`. `second_factor` requires the pending state and lists the pending user's credentials in `allowCredentials`. `reauth` requires a session with strength `mfa` and lists the current user's credentials. The response body is the options JSON of step 6, and the ceremony id goes into the session (step 5). A purpose whose precondition fails answers 401 with `authentication_failed`. With `LOCAL_ACCOUNTS=false`, the purpose `sign_in` answers 404 like the password route of 0004, and the purposes `second_factor` and `reauth` stay available for federated users with a local passkey.
    - `POST /api/auth/passkey` takes an AuthenticationResponseJSON, consumes the `sign_in` challenge, calls `Passkeys.authenticate/4` without `expected_user` (which refuses owners with an external identity, step 8), and calls `UserAuth.log_in_user(conn, user, auth_methods: [:passkey], strength: :mfa, mfa_at: now)`. It answers 200 with the body of `GET /api/session`, or 401 with `authentication_failed` for every failure. With `LOCAL_ACCOUNTS=false`, it answers 404 before any verification.
    - None of these endpoints switches to another factor on its own; the person chooses the factor in the UI (0011).

16. **Recovery.** `Espalier.Accounts.Recovery`:
    - `POST /api/auth/recovery/start` takes `{"email": ...}` and always answers 202 with the same body. Every request causes one lookup by `email_hash` and one job insert into the `mail` queue, so known and unknown addresses lead to the same database work and the same response (README section 6.10). 18. **Failure counters and throttling.** Use the `FailureCounters` functions of 0004 with the kinds `:totp`, `:recovery_code` and `:passkey` (README section 6.10: from the fifth consecutive failure each attempt waits longer, 30 seconds doubling up to one hour; after 50 failures the authenticator stays disabled until a recovery completes; a success resets the counter). ## Notes
- `wax_` 0.7.0 (Hex, 2025-05-18; source github.com/tanguilp/wax) has one maintainer and no independent security review, according to its README. Its documentation states a challenge timeout of `20 * 60` seconds, and `Wax.Challenge` sets `timeout: 120` (issue #58), so every call passes `timeout: 300` and the browser gets 300000 ms, the default that WebAuthn Level 3 recommends. Issue #59 reports that `Wax.register/3` accepts any COSE algorithm, RS1 (-65535) included; issue #60 reports that `crossOrigin` and `topOrigin` are dropped and that BS without BE is accepted; issue #61 and PR #62 report exceptions on malformed clientDataJSON. Each of these is a check in step 9.
- `wax_` 0.7.0 ties the attestation format to the requested conveyance: with `"none"`, a response with `packed` and `x5c`, `tpm`, `android-key` or `fido-u2f` fails with `:invalid_attestation_conveyance_preference`, and with `"direct"`, the format `none` of synced passkeys fails (issue #51, fix in the open PR #55). The platform requests `"none"` in every ceremony.
- `wax_` 0.7.0 always requires the UP flag at registration. The SPA in 0011 therefore cannot use `useAutoRegister` of `@simplewebauthn/browser`. Conditional UI requests sign-in options on page load; a challenge expires after 300 seconds, so the SPA requests new options when a sign-in fails after that time.
- No public report covers `wax_` 0.7.0 on Elixir 1.20.4 with OTP 28.5, which is why step 1 comes first. `wax_` 0.7.0 requires `x509 ~> 0.8`, which admits 0.9.x, and x509 0.9.0 (2025-06-20) added OTP 28 support and requires OTP 28.0.1 or later (x509 CHANGELOG).
- NIST SP 800-63B-4 (July 2025): section 3.1.2 requires look-up secrets to be used once and stored hashed; section 4.2.1.1 requires at least 64 bits for saved recovery codes and the issue of a new code after a recovery, which step 12 implements with a new set of ten; section 3.2.2 caps consecutive failures per authenticator at 100. At AAL2 a verifier offers at least one phishing-resistant option, and in this stack only passkeys are phishing-resistant.
- ASVS 5.0.0 6.5.5 limits the lifetime of a TOTP code to 30 seconds. README section 6.6 accepts the previous step, as RFC 6238 section 5.2 recommends ("at most one time step is allowed as the network delay"), and the matrix records it as a deviation (README section 15, decision D15).
- ASVS 5.0.0 11.5.1 asks for at least 128 bits from a CSPRNG for values that must not be guessable. Recovery codes carry 128 bits (16 bytes, 26 base32 characters, README section 6.6), WebAuthn challenges 256 bits and user handles 512 bits. At 112 bits or more, ASVS 6.5.2 allows a standard hash for look-up secrets, so HMAC-SHA256 with a server key suffices and no password hash is needed. The last of the 26 characters carries 3 bits of the code and 2 zero bits, so it is one of `A`, `E`, `I`, `M`, `Q`, `U`, `Y` and `4`.
- ASVS 5.0.0 6.4.3 requires that a password reset does not bypass an enabled second factor, and 6.6.2 requires that an out-of-band code works only for the request it was issued for.
- NimbleTOTP 1.0.0 and eqrcode 0.2.1 print compile warnings on Elixir 1.20 (open PRs nimble_totp #44 and eqrcode #35). The warnings come from the dependencies and do not fail `mix compile --warnings-as-errors` of the project.
- The OWASP Logging Vocabulary has no event for the enrollment of a factor. Step 20 maps factor changes to `user_updated` with a `change` field and keeps every event name inside the vocabulary.
- Playwright stays at 1.59.1 to match `playwright-driver` in the pinned nixpkgs. The cross-browser `browserContext.credentials` API needs 1.61, so the spike and the end-to-end tests of 0011 use the Chromium DevTools `WebAuthn` domain. Its defaults are `hasResidentKey: false`, `hasUserVerification: false` and `isUserVerified: false`, which is why step 1.4 sets all three. The domain offers `setUserVerified` to switch the result of user verification and `setResponseOverrideBits` with `isBogusSignature`, `isBadUV` and `isBadUP` to alter a response for server-side flag tests. WebAuthn Level 3 section 6.3.3 requires user verification in the authorization gesture when the request asks for it, so a virtual authenticator whose user verification fails cannot answer a `"required"` request; step 1.4 therefore clears the UV bit through `setResponseOverrideBits` and keeps a fallback with `"discouraged"` browser options.
