## Goal
People sign in, enroll their factors, recover access and manage their account
security in the SPA. The sign-in page offers passkeys with conditional UI, the
password with a second factor, the configured OIDC and LDAP providers and, on
demo instances, the demo accounts. An invitation leads to an enrollment wizard
that ends with saved recovery codes. The security page lists passkeys, the
authenticator app, the remaining recovery codes, password, e-mail, connected
directory and OIDC accounts and active sessions, and every change passes a
step-up with a second factor when the API asks for one. Before a provider is
connected, the page states that the account then signs in through that provider
only. Sign-out follows the
provider's logout URL where 0006 returns one. The SPA keeps no token and no
personal data in browser storage, keeps its CSRF token current in every tab,
and passes axe checks in English and German. Playwright covers each pathway
with the Chromium DevTools virtual authenticator, Mailpit, the mock OIDC
provider and lldap.

## Security requirements
The ownership table of the verification matrix (0004 step 42) makes this task the owner of these rows:
- ASVS 6.2.6: password fields use `type="password"` with a button that reveals the value temporarily.
- ASVS 6.2.7: password fields allow paste and carry `autocomplete` values for password managers.
- ASVS 14.2.1: e-mail link tokens and the OIDC sign-in ticket travel in the URL fragment and in request bodies, so no request URL contains them. Two values of the OIDC flow travel in a query string: the authorization response (`code`, `state`) of the callback and the intent of 0006 (`/auth/oidc/<key>?intent=<token>`). The matrix row records both as a deviation with the measures of 0006: the code and the intent work once, the intent expires after 5 minutes and works only with the browser session that created it, the code is bound to the PKCE verifier, and `filter_parameters` keeps `code`, `state` and `intent` out of the logs.
- ASVS 14.3.1: sign-out, a 401 and a `signed-out` message from another tab clear the query cache and every component state that holds account data.
- ASVS 14.3.3: the row lists the browser storage keys of this task and of 0010: the theme (`localStorage` key `theme`, 0010), the language (`i18nextLng`, 0010) and, during an OIDC redirect, the return path (`sessionStorage` key `espalier.return_to`, step 5). 0012 (step 2) and 0014 (step 11) extend the row for the keys they write. No session token, CSRF token, recovery code, TOTP secret, e-mail address or display name reaches browser storage.

The SPA code and the tests of this task also extend these rows; the task in parentheses owns the row:
- ASVS 3.2.2 (0010): account pages render server values as React text, and the TOTP QR code renders as an `<img>` with a data URL.
- ASVS 3.5.1 (0004, also extended by 0010): after every session change the SPA refetches the CSRF token, and other tabs refetch it through `BroadcastChannel`.
- ASVS 6.2.2 and 6.2.3 (0004): users change their password in a form that asks for the current and the new password.
- ASVS 6.2.9 (0004): the SPA accepts passwords up to 128 code points and sets no `maxLength` on password fields. Its counter counts code points after NFC normalization, as the server does (0004 step 14, README section 15, decision D12).
- ASVS 6.3.3 (0005): an enrollment or recovery session reaches no page other than the enrollment wizard until a factor exists.
- ASVS 6.3.8 (Level 3, selected in README 6.1; 0004): sign-in, invitation, recovery and e-mail change show the same text for every failure.
- ASVS 6.5.6 (Level 3, selected; 0005): users remove any passkey and the authenticator app, except the last remaining second factor.
- ASVS 7.4.3 (0004): after a factor change and after recovery, the SPA offers to end all other sessions.
- ASVS 7.4.4 (0010): the security page has its own sign-out button in addition to the header of 0010.
- ASVS 7.5.1 (0004): changes to e-mail, password, factors, recovery codes and linked accounts pass the step-up dialog when the API answers with `RECENT_AUTH_ERROR_CODE`, the code `reauth_required` of `require_recent_auth/2` (README 6.10 and 6.12).
- ASVS 7.5.2 (0004): users see their active sessions and end them after a step-up.
- ASVS 7.6.1 (0006): sign-out follows the `logout_url` of an OIDC session, so the provider session ends as 0006 documents.
- ASVS 7.6.2 (0004): a session starts only after an explicit user action; conditional UI waits until the user picks a passkey, and the invitation page waits for a click.

## Notes
- `@simplewebauthn/browser` 14.0.0 was published on 2026-09-02 (npm registry). The code of the 14.0.0 package shows these behaviours. `startAuthentication` with `useBrowserAutofill` throws when the browser lacks conditional mediation and, by default, when no `input[autocomplete$='webauthn']` exists. Every call aborts the previous ceremony through `WebAuthnAbortService`, and `cancelCeremony()` aborts it by hand. `cancelCeremony()` acts only on a controller that exists and then clears it (`esm/helpers/webAuthnAbortService.js`), so a run whose options request is still pending holds no controller to abort; step 6 therefore checks `active` after each `await`. An abort surfaces as `WebAuthnError` with code `ERROR_CEREMONY_ABORTED`, and a `NotAllowedError` keeps its `name` with code `ERROR_PASSTHROUGH_SEE_CAUSE_PROPERTY`. `startRegistration` and `startAuthentication` encode the credential themselves and never call `toJSON()`.
- `wax_` 0.7.0 checks the UV flag only with `user_verification: "required"` and always requires the UP flag at registration (`wax_` 0.7.0 source and documentation, retrieved 2026-10-07; 0005 Notes). `useAutoRegister` creates passkeys without user presence, so this server rejects them.
- Playwright stays at 1.59.1 to match `playwright-driver` in the pinned nixpkgs (README section 3). `browserContext.credentials` arrived in 1.61 (release notes); it replaces `navigator.credentials` in JavaScript and, in 1.63, returns credentials whose `toJSON()` yields an empty response (Playwright source). This task uses neither. The tests drive the browser's own WebAuthn stack through the CDP `WebAuthn` domain, which is experimental and available in Chromium only, and the SPA sends the objects that SimpleWebAuthn returns.
- The CDP defaults are `hasResidentKey`, `hasUserVerification` and `isUserVerified` false, so `addAuthenticator` sets all three. The protocol definition (`WebAuthn.pdl` in the devtools-protocol repository) lists the commands `setUserVerified`, `setResponseOverrideBits` (with `isBadUV`), `setAutomaticPresenceSimulation`, `getCredentials` and `addCredential` and the options `defaultBackupEligibility` and `defaultBackupState`. Check each parameter name against the protocol of the Chromium build that ships with `playwright-driver` before writing the specs.
- `otpauth` 9.5.2 (npm) generates codes from an `otpauth://` URI in Playwright; step 2 checks the declared return type of `URI.parse` in the installed package. The server stores the last used TOTP step and accepts the current and the previous step (README 6.6, 0005 step 10). The confirmation code is then used, so the spec waits for the next step before it signs in.
- Mailpit v1.31.4 serves `GET /api/v1/search?query=to:...` (0004 step 46 uses it) and, according to its API documentation, `GET /api/v1/message/{ID}` with the plain text in `Text`. Step 18 checks both against the running container before the helper is written. Invitation, recovery and e-mail change mails go out through Oban (README 6.3), so the helper polls for up to 15 seconds.
- openapi-fetch 0.17.0 declares a `fetch` option of type `(input: Request) => Promise<Response>` and passes each middleware a `Request` (`dist/index.d.ts` of the 0.17.0 package; step 2 checks the installed version). 0010 uses that option for `fetchImpl`.
- NIST SP 800-63B-4 section 3.1.1.2 states that a CSP SHALL provide the reason when it rejects a password from the blocklist and that verifiers SHALL offer guidance for choosing a strong password. Steps 9 and 12 show the error code of 0004 under the field and the guidance next to it.
- 0005 generates recovery codes at every completed enrollment, also for users with an OIDC or LDAP identity (step 12, `Factors.complete_enrollment/3`), and `POST /api/auth/second-factor` accepts `recovery_code` for every pending state (step 14). README 6.6 lets a recovery code serve as second factor at sign-in, and the OIDC and LDAP rows of the README 6.2 table and the diagrams `auth-oidc.puml` and `auth-ldap.puml` name passkey, TOTP and recovery code as second factor after a federated first factor. The SPA therefore offers the recovery code after the password, OIDC and LDAP, so federated users can use the codes that the wizard made them save.
- The ASVS IDs come from the chapters V3, V6, V7 and V14 of OWASP ASVS 5.0.0 at tag `v5.0.0_release` of the OWASP ASVS repository (V14: `5.0/en/0x23-V14-Data-Protection.md`).
- The fragment of a URL never reaches the server and is not part of the Referer header, which is why README 6.4 puts e-mail tokens there. `takeFragmentParam` also removes it from the address bar and the history entry.
- A step-up through the identity provider (`idp_trusted`) leaves the page, so the pending change is lost and the user repeats it after the return. Local step-ups keep the page and repeat the request.
- Password sign-in (0004 step 16), discoverable passkey sign-in (0005 step 8) and recovery (0005 step 16) serve only accounts without an external identity, so an account reaches the platform through its linked providers once it holds one. README section 8 lists no route that removes a linked identity, and the admin reset of decision D11 (0015) removes the factors and keeps the identity. The confirmation of step 12 therefore states these consequences before the link, and the security page reads `linked_providers` to hide the password and e-mail forms of such an account.
- The security page offers no in-place replacement of the authenticator app. A person whose only factor is the app adds a passkey before removing it, or uses recovery, where a new TOTP setup replaces the old factor (0005 step 10).
- The e2e suite signs in about twenty times from one address. When the Hammer limits of 0004 to 0007 answer 429 during a run, raise the limits in `config/dev.exs` only.
